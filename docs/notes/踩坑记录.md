# 踩坑记录

> 这份文档记的是**「不报错但结果不对」的坑**。
>
> 为什么专门记这类：写错代码会报错，改错代码不会。控制台干净、构建成功、
> 测试全绿，而结果就是不对——这类问题只能靠「知道有这个坑」来省时间。
>
> 每条按四段写：**症状 → 真因 → 判据（怎么确认是这个坑）→ 怎么避免**。
> 判据那栏最重要：它告诉你下次怎么在 30 秒内认出它，而不是又从头猜一遍。

## 1. 管道过滤器会杀掉上游进程

**症状**：改完代码重新打包，手机上「没生效」。反复重启 app、清缓存、
重装都无效。日志里 `BUILD SUCCESSFUL` 一路正常。

**真因**：用了这样一条命令过滤构建输出：

```powershell
node build_apk.mjs | Select-String "BUILD SUCCESS" | Select-Object -First 3
```

`Select-Object -First N` 会**终止上游管道**——拿到 3 行之后，
它往 node 进程发一个中止信号。构建完成了，但脚本**还没走到 `adb install`
就被杀掉了**。手机上装的是上一个包。

**判据**：对比本机 `dist/assets/` 里的 js 文件名，和设备上
`document.scripts[0].src` 的文件名：

```bash
# 本机
Get-ChildItem dist\assets\*.js | Select-Object -ExpandProperty Name
# 设备上
node android.mjs probe "[].slice.call(document.scripts).map(function(e){return e.src.split('/').pop()})"
```

两个文件名不一致 = 装的不是这次的包。

**怎么避免**：
1. **过滤构建输出时不要用 `-First`**。要看哪几行就 `Select-String`（不加 `-First`），
   或 `Select-Object -Last N`（`-Last` 也要小心，它同样会等够才输出，但不会提前杀）。
   最保险：**别过滤**，全看。
2. 在 `build_apk.mjs` 里加**自检**：打包完从 APK 里读出 `index.html`，
   核对它引用的 js 文件名是不是本次构建的，对不上直接抛错。
   现在这个自检已经加进去了：

   ```text
   · 自检通过：APK 内是本次构建的 index-Cn2njUzx.js
   ```

3. 养成习惯：**改完先确认设备上跑的文件名变了**，再开始验证功能。

> 同类问题：任何 `| Select-Object -First N` 跑在长时间任务上都有杀掉上游的风险。

## 2. Gradle `UP-TO-DATE` 不等于打包是新的

**症状**：看到 `33 actionable tasks: 33 up-to-date` 就怀疑 Gradle 没重新打包，
于是去 `gradle clean`，怀疑自己的复制逻辑。

**真因**：`UP-TO-DATE` 是**正常的**。本次前端产物没变化，Gradle 跳过打包是对的。
在这个项目里那次 UP-TO-DATE 是无辜的，真正的原因是坑 1。

**判据**：直接看 APK 里装了什么，别看 Gradle 说了什么：

```powershell
Add-Type -AssemblyName System.IO.Compression.FileSystem
$z=[IO.Compression.ZipFile]::OpenRead('app-debug.apk')
$e=$z.Entries|Where-Object {$_.FullName -eq 'assets/index.html'}
$sr=New-Object IO.StreamReader($e.Open()); $sr.ReadToEnd(); $sr.Close(); $z.Dispose()
```

里面引用的 js 文件名跟 `dist` 对得上，就说明 Gradle 没问题。

**怎么避免**：判断「APK 里是不是新代码」只有一个可靠办法——
**读 APK 内容**，不要读构建日志。

## 3. `setStatusBarColor` 在 Android 15+ 是空操作

**症状**：主题里写了不透明的状态栏颜色，截图里状态栏底下还是透出页面的渐变。
改 `statusBarColor` 改到崩溃也没用。

**真因**：targetSdk ≥ 35 时 Android **强制 edge-to-edge**，
`statusBarColor` / `navigationBarColor` 被废弃成空操作。
状态栏下方画什么，它就透什么。

**判据**：真机 `ro.build.version.sdk ≥ 35` 就能复现。

**怎么避免**：**不透明的状态栏只能由页面自己画**——一条固定在顶部的实色带：

```css
.sb {
  position: fixed;
  top: 0; left: 0; right: 0;
  height: var(--wb-sb-h);
  background: var(--wb-bg);
  z-index: 999;
  pointer-events: none;
}
```

原生侧只负责把两代标志都设成实色（`APPEARANCE_LIGHT_STATUS_BARS`
保证深色图标），别指望它挡内容。

## 4. `LAYOUT_FULLSCREEN` 会吃掉 IME insets

**症状**：键盘明明弹了（`mInputShown=true`、ime inset bottom = 991 物理像素），
但页面里 `visualViewport.height` / `innerHeight` / `clientHeight`
**全都纹丝不动**（还是 800）。键盘高度算出来恒为 0，
输入框被键盘盖住，而 JS 里连一个异常都没有。

**真因**：为了做「沉浸式」设了 `LAYOUT_FULLSCREEN`，
而**全屏标志会让系统消费掉 ime 类型的 inset**。
另外全屏下 WebView 的窗口尺寸从头到尾不变，insets 也就不会重分发。

**判据**：把系统量和 JS 量并排看，对不上就是这个坑：

```bash
adb shell dumpsys input_method | Select-String mInputShown   # true = 键盘弹了
node android.mjs probe "JSON.stringify({innerH:innerHeight, vv:Math.round(visualViewport.height)})"
```

**怎么避免**：**别用 LAYOUT_FULLSCREEN**。改成系统默认的「不覆盖」布局：
状态栏实色、WebView 从状态栏下方开始。这样 `adjustResize` 才会压缩视口，
标准做法自然恢复；万一还测不到（见坑 5），再用原生轮询兜底。

## 5. insets 回调可能一次都不来

**症状**：监听器装好了、`requestApplyInsets()` 也调了，键盘弹起却
一次回调都没有（logcat 里一条日志都没有）。

**真因**：Insets 只在窗口尺寸、焦点等状态变化时重分发。
全屏模式下 WebView 尺寸永远不变，于是永远不重分发。

**判据**：监听器里打一行 log，弹一次键盘，看有没有输出。

**怎么避免**：**不能只靠监听，要轮询兜底**：

```java
target.post(new Runnable() {
    public void run() {
        WindowInsets insets = target.getRootWindowInsets();
        if (insets != null) updateIme(insets);
        target.postDelayed(this, 250);   // 键盘动画本身要几百毫秒，再密只是白烧电
    }
});
```

## 6. `getInsetsController()` 会空指针

**症状**：一启动就崩，堆栈是

```
java.lang.NullPointerException: Attempt to invoke virtual method
'WindowInsetsController DecorView.getWindowInsetsController()' on a null object reference
  at PhoneWindow.getInsetsController(PhoneWindow.java:4341)
  at MainActivity.applyImmersive(MainActivity.java:211)
```

堆栈完全指不到原因（看不出是「调用时机」问题）。

**真因**：`getWindow().getInsetsController()` 内部会去取 DecorView，
而 `onCreate` 开头 DecorView 还没创建。

**怎么避免**：所有窗口级设置放到 **`setContentView` 之后**。

## 7. `ViewCompat.OnApplyWindowInsetsListener` 不是嵌套类

**症状**：编译报「找不到符号：OnApplyWindowInsetsListener」。

**真因**：它是独立顶层接口（`androidx.core.view.OnApplyWindowInsetsListener`），
不在 `ViewCompat` 里面。写成嵌套类编译不过。

**怎么避免**：minSdk 24 时直接用 platform 版
（`android.view.View.OnApplyWindowInsetsListener`），顺手也避免了 API 30 分支。

## 8. `overscroll-behavior` 必须写在 `html` 上

**症状**：下拉页面到顶再用力拉，整个页面（连同 `position:fixed` 的底栏和顶栏）
被一起拖出屏幕。用户说「底栏跑到页面外面去了」「标题也飘了」——
而 CSS 里两处都是 fixed，看起来不该动。

**真因**：默认滚动容器是 `<html>`，不是 `<body>`。
把 `overscroll-behavior` 写在 body 上**等于没写**。实测：

```
body → overflow-behavior-y: "none"     ← 我设了
html → overflow-behavior-y: "auto"     ← 实际还是这个
```

**怎么避免**：写在 `html` 上，并且用 `contain` 而不是 `none`
（`contain` 不把「继续拉」传给系统，某些机型上系统会接管这一步，
表现为整页被系统的下拉刷新 UI 带走）。

## 9. 同一处留白只能算一次

**症状**：某些页面标题离状态栏明显比其他页面远；或顶部凭空多一段空白。

**真因**：容器和它内部的 sticky 条**都加了**同一个安全区变量：

```css
.wb-page   { padding-top: var(--wb-sb-h); }   /* 38px */
.wb-topbar { padding-top: var(--wb-sb-h); }   /* 又 38px —— topbar 是 page 的第一个子元素 */
```

叠加 = 76px。实测标题落在 84px（应为 46px）。

同类问题：想给**底部**固定条让位，却插了一个空 `<div>` 到容器**最上面**，
顶部凭空多出 56px 空块。

**怎么避免**：定一条规矩并写进注释——**有 topbar 的页面由 topbar 让位，
没有的由页面自己让**；底部让位用 `padding-bottom`，不留多余元素。

**判据**：量「首个元素的 top」和「topbar 下沿」的差值，各页应该一致。

## 10. `overflow-x: clip` 在根元素上不生效

**症状**：页面比屏幕宽，能横向拖（`scrollWidth 440` vs `innerWidth 360`），
用户说「背景比屏幕宽」。加 `overflow-x: hidden/clip` 都没用。

**真因**：根元素的 `overflow-*` 会**传播给视口**，而根元素自身的计算值
**恒为 `visible`**。所以 `getComputedStyle(document.documentElement).overflowX`
永远告诉你 `visible`，看不出有没有生效；而且这个 WebView 里视口不采用
body 的 overflow。

**怎么避免**：在**真正产生溢出的那个元素**上夹。这里是首页的装饰光斑
（故意 `right:-80px` 出血配合 blur），所以夹在 `.home` 上：

```css
.home { overflow-x: clip; }   /* 不是 html，不是 body */
```

**判据**（比看 computed 值可靠）：

```bash
node android.mjs probe "JSON.stringify({scrollW:document.documentElement.scrollWidth, innerW:innerWidth})"
```

**另一个陷阱**：`querySelectorAll('*')` **查不到伪元素**，
所以「遍历所有元素找谁越界」这种诊断手段在这里会得到「没有越界元素」
的假阴性。伪元素只能用 `getComputedStyle(el, '::before')` 看到。

## 11. `overflow-x: hidden` 会把另一轴变成 `auto`

**症状**：给一个 flex 容器加 `overflow-x: hidden` 想夹住横向溢出，
结果页面变成了「在容器内部滚」，底部固定条和安全区计算全乱。

**真因**：规范规定——一轴是 `visible` 而另一轴不是时，
`visible` 会**计算成 `auto`**。于是元素成了滚动容器。

**怎么避免**：用 `overflow-x: clip`。`clip` 不建立滚动容器，也不强制另一轴变 `auto`，
竖向照常由文档流滚，sticky 也不受影响。

## 13. `sticky` 会被祖先的 `overflow` 废掉

**症状**：滚动时标题跟着滚出屏幕。

**真因**：`position: sticky` 相对**最近的滚动容器**定位。
某个祖先一旦开了 `overflow: hidden/scroll/auto`，sticky 就相对那个祖先，
而不是视口。

**怎么避免**：
- 粘顶元素显式写 `overflow: visible` 兜住
- 注意坑 11 的连锁：`overflow-x: hidden` 也会创建滚动容器，
  可能间接把 sticky 弄坏

## 14. 短路求值会毁掉响应式依赖收集

**症状**：拖拽排序**只有松手后顺序才变**，拖动过程中一行像素都不动。
控制台干净，没有报错。

**真因**：

```js
function styleFor(k, index) {
  if (!active || rects.length === 0 || key.value == null) return {}   // ← 这里
  ...
  transform: `translateY(${offset.value}px)`   // 永远走不到
}
```

Vue **只在渲染时真正读到**的 ref 上建立依赖。
初始渲染时 `active` 是 `false`，`||` **短路**，第一项就为真直接 return——
`key` / `to` / `offset` **一个都没被读到**，于是这三个 ref 从未被订阅。
拖动时改它们不触发任何重渲染。

松手之所以「看起来正常」，是因为 `onUp` 调了 `load()` 整表刷新，
最终状态自然是对的——**中间过程一个像素都不动**。

**判据**（这个 bug 唯一的出路）：
**在拖动过程中分别量「DOM 上的 transform」和「手动调用 styleFor 的返回值」**。
两者不一致 = Vue 算了样式却没写进 DOM；两者一致但 DOM 仍为空 =
响应式根本没接上。

```js
// 拖动中途，在页面里
[].slice.call(document.querySelectorAll('.sent')).map(e => ({
  computed: getComputedStyle(e).transform,
  inline: e.getAttribute('style'),
}))
// 再手动调一次 styleFor，对比两者
```

**怎么避免**：
1. 把所有响应式状态**先读到局部变量**，再判断：

```js
const dragging = key.value != null && rects.length > 0 && active
const dy = offset.value        // ← 先全部读到，建立依赖
const target = to.value
if (!dragging) return {}
```

2. 通用规则：**渲染函数里的任何早退分支，都不能挡住 ref 的读取。**
   需要的话用一个不短路的写法先把依赖收集掉。

> 这类 bug 极其安静，也极其通用：任何「渲染期计算 + 早退」都可能中招。

## 15. scoped 样式选不中 teleport 出去的组件

**症状**：给弹层（`van-popup`）加样式，规则完全不起作用，
但**没有任何报错**，devtools 里也看不到那条规则命中。

**真因**：`<style scoped>` 会把选择器编译成
`.kb-open[data-v-x] .van-popup[data-v-x]`。
而 `van-popup` 被 **teleport 到 `body`**，拿不到组件的 `data-v` 属性，
永远匹配不上。

**怎么避免**：需要作用于 teleport 出去的元素时，**写在全局样式里**。
判断方法很简单：**这个元素会不会出现在别的组件的 DOM 位置上？**
会的话就别写在 scoped 块里。

## 17. 坐标换算：CSS 像素 vs 物理像素

**症状**：点了没反应，或者点到了隔壁控件。**没有任何报错**。

**真因**：两个单位差一个 `devicePixelRatio`（这台机器 3.5）：

| 你手里的数 | 单位 | 本机实际 |
|---|---|---|
| 截图上的像素 | 物理像素 | 1080 × 2400 |
| 网页里量到的坐标 | CSS 像素 | 360 × 800 |

```bash
# 错：把 CSS 坐标当物理坐标
adb shell input tap 180 582        # 点到别处，而且不报错
adb shell input tap 630 2037       # 对
```

**怎么避免**：**永远不要用「看着截图估出来的坐标」点击**。
要么让程序量，要么用选择器。封装好的命令：

```bash
node android.mjs rect  ".big"      # 同时给出 CSS 和设备两种坐标
node android.mjs tap   ".big"      # 点元素中心，自动乘密度
node android.mjs tapxy <x> <y>     # 按 CSS 坐标点，工具负责换算
```

## 18. `adb input swipe` 测不了长按

**症状**：想自动化验证「长按拖动排序」，结果永远触发不了。

**真因**：`input swipe` **一开始就在移动**。而拖动逻辑有 8px 容差
（「长按还没成立就先动了 = 这是划词/滚动，放弃」），
所以它每次都被判定成滚动并取消。

**怎么避免**：用 CDP 直接派发真实触摸序列——
`touchStart` → 静止等待 → 逐步 `touchMove` → `touchEnd`：

```js
await send('Input.dispatchTouchEvent', { type: 'touchStart', touchPoints: [{ x, y, id: 1 }] })
await sleep(520)                       // 必须先静止按住
for (let i = 1; i <= 10; i++) {
  await send('Input.dispatchTouchEvent', { type: 'touchMove', touchPoints: [{ x, y: y + i * step, id: 1 }] })
  await sleep(40)
}
await send('Input.dispatchTouchEvent', { type: 'touchEnd', touchPoints: [] })
```

## 19. `JSON.stringify(promise)` 得到空对象

**症状**：所有异步查询都返回 `{}`，同步的正常。一看代码没问题。

**真因**：`JSON.stringify(asyncFn())` 是**同步**求值的，
Promise 被直接字符串化成 `"{}"`。后面给 CDP 传 `awaitPromise: true` 也救不了
——那时 promise 已经被 stringify 过了。

**怎么避免**：**先 await 再 stringify**：

```js
expression:
  '(async function(){ try { return JSON.stringify(await (' + expr + ')) }' +
  ' catch(e) { return JSON.stringify({__err:String(e)}) } })()',
returnByValue: true, awaitPromise: true,
```

## 22. 键盘弹起时只有第一次会避让

**症状**：第一次点输入框能自动避让，第二次就不动了。收起键盘再点，还是不动。

**真因**：基准值没在键盘收起时回退：

```js
watch(keyboardInset, (kb) => {
  if (kb <= last) return    // ← 收起时(283→0)命中这里直接返回，last 没更新
  last = kb
})
```

第一次：kb `0→283`，`283 > 0` 滚动，`last = 283`。
收起：`283→0`，`0 <= 283` 提前返回，**`last` 停在 283 不回退**。
第二次弹起：`283 <= 283` 又命中 —— 从此再也不滚。

**怎么避免**：**先无条件更新基准，再判断方向**：

```js
watch(keyboardInset, (kb) => {
  const rising = kb > last
  last = kb          // ← 无条件
  if (rising) keepVisible(focused, 360)
})
```

**顺便**：避让最好挂在**全局 `focusin`** 上，不要逐个输入框挂钩子。
因为有个逐个挂法覆盖不到的情况——**键盘已经开着，用户从 A 框点到 B 框**，
此时键盘高度没变化，没有 inset 回调可等，只有 focusin 能救。

## 27. 提交顺序错了会出现「错位中间帧」

**症状**：拖动排序松手时，列表项**先弹回原位、过几十毫秒才排成新顺序**。
快速连续换位时整列看起来在闪，像是状态乱了。日志、数据库、
最终结果**全都是对的**——只有中间那一下不对。

**真因**：`onUp` 里的顺序写反了：

```js
reset()              // ① 先清 transform → 行瞬间弹回旧位置
await onReorder(f,t) // ② 落库 + 重新渲染 → 几十毫秒后才排成新顺序
```

① 和 ② 之间有一段空窗：位移已经没了、内容还是旧的。
真机逐帧采样量到的实况：

```
+1759ms  位移已清空、内容还是旧顺序
+1808ms  内容才换成新顺序          ← 50ms 的错位窗口
```

**判据**：肉眼很难稳定复现，**必须逐帧采样**。在页面里挂
`requestAnimationFrame`，每帧记录一次「内容顺序 + 各行位移」，
只记录和上一帧不同的那些：

```js
function sample(){
  var rows = [].slice.call(document.querySelectorAll('.sent'));
  var sig = rows.map(r => r.querySelector('.en').textContent).join('|')
             + ' TF:' + rows.map(r => getComputedStyle(r).transform).join(',');
  var last = frames[frames.length-1];
  if (!last || last.sig !== sig) frames.push({t: now(), sig});
  requestAnimationFrame(sample);
}
```

> MutationObserver 在这里不可靠：跨组件重渲染、teleport、style 属性变更
> 都容易漏记或重复记。**逐帧采样才能看到「被画出来」的每一帧。**

**怎么避免**：**先改数据，再清位移**。两者落在同一个 Vue 批次里，
底层顺序已经和手指放开时看到的一致，去掉位移视觉上零跳动：

```js
// onReorder 开头是同步的：先换掉本地数组
sents.value = [...swap(sents.value, from, to)]
// 之后才 await 落库
await reorderSentences(...)

void onReorder(f, t)   // 故意不 await
reset()                // 紧接着清 transform
```

修复后逐帧采样只剩一帧，位移清空与内容更新同时发生。

## 28. 测试自己有随机性：一次通过不代表对

**症状**：全量回归跑出 2 个 FAIL，但连跑 9 次都通过。

**真因**：测试里出题是**随机抽卡**的，而断言写死了某个分数，
依赖「恰好抽到哪一张」。这是测试自身的缺陷，不是产品代码的问题。

**怎么避免**：
- 随机性的测试要固定随机源（注入 seed），否则不可复现
- 断言不要依赖随机结果，要断言**不变量**（比如「选项不重复」
  「正确释义在选项里」），而不是「这次算出来是 18.18 分」
- 遇到偶发 FAIL，先连跑若干次判断是稳定复现还是抖动

> 这条也是写给未来的自己：**「跑过一次」不等于「通过」。**

## 29. 要验证「有没有闪」必须逐帧采样

**症状**：肉眼看着「好像闪了一下」，但说不清闪的是什么；
截图只能抓到某一帧，复现不了。

**真因**：中间状态往往只存在**一两帧**（~16-32ms）。
截图、录屏、甚至 `getBoundingClientRect` 的单次采样都可能恰好错过。

**怎么避免**：在页面里挂 `requestAnimationFrame` 循环，
每帧记录一次关键状态，**只记录和上一帧不同的**，结束后打印全部。
见 [坑 27](#27-提交顺序错了会出现错位中间帧) 的判据一栏。

要点：
- 状态签名要把**内容**和**位移**都算进去。只记内容会漏掉「位移跳了但内容没变」，
  只记位移会漏掉「内容错了但没动」
- MutationObserver 在跨组件重渲染 / teleport / style 属性变更时不可靠，
  **逐帧采样才是「被画出来的那一帧」的准确记录**
- 记录要在动作**之前**就挂好，跑完立刻断开；
  忘了断开会积累残留的采样器，下一次运行往同一个数组里推旧格式的记录，
  然后报一个看起来毫不相关的错（这个我也踩了一次）

## 30. Java 块注释里写 `*/*` 会提前结束注释

**症状**：加了一段带注释的新方法之后，`gradle assembleDebug` 报
`错误: 非法字符: '，'`、`错误: 需要 ';'`，一行接一行几十个，
而且报错行号全都落在**注释中间的中文**上。

**真因**：注释里写了 mime 通配符 `*/*`。它同时包含 `*/`，
于是 javac 认为块注释在这里就结束了，后面的中文全被当成代码解析。
控制台又是 GBK，中文错误信息本身是乱码，
于是第一反应是「是不是文件编码写错了」——**方向完全错了**，
我去查了一堆编码设置，真正的错误只有三个字符。

**怎么避免**：
- 注释里要提到通配符/正则/`*/` 时，**把它拆开写**：
  「mime 设成通配符（星号、斜杠、星号）」，或用全角字符代替。
- 判据：**报错行号全在注释里 + 错误是「非法字符」而不是「找不到符号」**
  → 基本可以断定是注释被提前结束，不是编码问题。

## 32. 数据没到就渲染「找不到」等于闪一下假话

**症状**：用户报「点进去一瞬间会闪一下别的界面，看不清」。

**判据（30 秒确认）**：挂 rAF 采样器打印每帧的「根元素 class + 首屏文字」，
跳转一次。真机输出：

```
t=2871933  wb-page           ← 单词页
t=2872400  wb-page gone      ← 「这个意思不在了，可能已删进回收站」  ← 它在闪
t=2872437  wb-page two-col   ← 真正的内容，37ms 后
```

**真因**：`sense.value` 初值是 `null`，而模板是 `<div v-if="sense">…</div>
<div v-else>「找不到这个意思」</div>`。读库要几十毫秒，这段时间
渲染的是**「找不到」分支** —— 一句假话。用户会以为刚点的义项被删了。

**怎么避免**：三段式，并且**读库期间不许说任何话**：

```ts
const loading = ref(true)
async function load() { loading.value = true; try { … } finally { loading.value = false } }
```

```
v-if="有数据" → v-else-if="loading" → 骨架屏 → v-else 「找不到」
```

骨架屏还要**留一条等高的空标题栏**：否则内容先顶到状态栏下面，
真页出来时整体下移一下 —— 跳动比闪文案更明显。
同样的坑在单词页是「这个词还没有释义」，在含义上一样假。

## 33. 同一路由不同 query，`onMounted` 不会重新挂载

**症状**：从错题板点「单挑这个意思」进训练页，回到底部「训练」tab 之后，

```ts
watch(() => route.query.solo, start, { immediate: true })
```

## 34. 文件选择器要用真触摸，合成 `click()` 不算用户手势

## 35. contenteditable 点一下就改，代价太高

## 36. 白字反色会把浅色高亮变成看不清

## 37. 拖动排序的合成验证

**症状**：`adb input swipe` 测不了长按拖动（[坑 18](#18-adb-input-swipe-测不了长按)）。

**怎么避免**：在页面里直接派发 **PointerEvent 序列**（不是 CDP 的触摸事件，
前者不依赖 `setPointerCapture`，`draglist.ts` 正好没用它）：

```js
const mk=(t,cy)=>new PointerEvent(t,{bubbles:true,cancelable:true,pointerId:1,pointerType:'touch',isPrimary:true,clientX:x,clientY:cy})
h.dispatchEvent(mk('pointerdown',y0))          // 序号（把手）
await new Promise(r=>setTimeout(r,500))        // 必须静止按住 >350ms
for(let i=1;i<=20;i++){ window.dispatchEvent(mk('pointermove',y0+15*i)); await sleep(25) }
window.dispatchEvent(mk('pointerup',y))         // window，不是把手
```

**断言不要比序号**：序号是 `数组下标+1`，重排后照样是 `1,2,3…`，
比它等于什么都没验。要比**内容**：

```js
const key = () => [...document.querySelectorAll('.sent .en')].map(e => e.innerText)
```

（我就用序号断言过一次，得到「顺序没变」的假结论。）

## 39. `push` 加 `back()` 可以围成一个环

**症状**：意思页左上角返回 → 单词页；单词页左上角返回 → **又回意思页**。
真机实测两次返回后 URL 原封不动，像返回键坏了。

**判据**：`history.length` 只增不减、而两次返回后 `location.hash` 一模一样。

**真因**：意思页的返回是 `router.push('/word/x')`（多压了一格历史），
单词页的返回是裸的 `router.back()` —— 两边对着来就成了环。

**怎么避免**（`src/nav.ts` 的 `goBack`，两页统一走它）：

```ts
export function goBack(router: Router, parent: string): void {
  const cur = router.currentRoute.value.path
  const prev = router.options.history.state.back   // push 记来源，replace 不动它
  const from = typeof prev === 'string' ? prev : ''
  if (window.history.length > 1 && from !== cur) router.back()   // 顶栏箭头 = 系统返回键
  else router.replace(parent)                                    // 兜底落点
}
```

两种不能 `back()` 的情况：
1. **没有上一层**（书签/桌面图标进来的深链，`history.length === 1`）——
   `back()` 是空操作，表现为「按了没反应」。真机实测：深链进单词页
   点返回，现在会正确落到 `/library`。
2. **上一层就是自己**（合并/删除义项后 `replace` 回同一页，历史里留下两条一模一样的
   单词页）—— 不处理的话就是「退到一模一样的地方」。

另外**合并/删除之后必须 `replace`**：那个义项已经不存在了，
再往回退只会退到「找不到这个意思」的页面。

## 40. 清测试数据要按主键删，并复核计数

**症状**：造了一批测试数据（14 义项 50 句）清理时，
`words`/`senses` 计数回到原值，**`sentences` 却还剩 50 条孤儿**。

## 41. 键盘避让把「元素顶部」当基准，差 2px 能滚 300px

**症状**：用户报「规避输入法过度 —— 输入法明明不到屏幕一半，
一碰输入框页面就窜到最顶上，内容都被推出屏幕」。

**判据**：量「键盘弹出前后 `scrollY` 变了多少」和「那个输入框实际被遮住了多少」。
真机：输入框只被盖住 **43px**，页面却滚了 **43px（修好后）** / 原来一次跳了 450px+，
甚至被 clamp 到 0 ——「刚打开的这一屏整个被换掉」。

**真因**（`keyboard.ts` 的 `keepVisible`，原式）：

```ts
const overflow = box.bottom - (keyboardTop - safeGap)
const target = Math.max(0, window.scrollY + box.top - overflow - 8)   // ← 这里
```

它把元素**顶部**当基准，而「刚好露出下沿」需要的滚动量只是 `overflow`。
`box.top` 越大，误差越大；而 `Math.max(0, …)` 会把向上的过量滚动
**悄悄吃掉**并表现成「页面窜到最顶」—— 代码看起来完全合理，只是算错了。

**怎么避免**：只挪被挡住的那一点，并夹到合法区间：

```ts
const limit = window.innerHeight - keyboardInset.value - BOTTOM_GAP
let delta
if (h > limit - TOP_GAP) delta = box.top - TOP_GAP            // 比可用区还高：露顶就认了
else if (box.bottom > limit) delta = box.bottom - limit       // 下沿被盖：往下挪正好那么多
else if (box.top < TOP_GAP) delta = box.top - TOP_GAP         // 上沿被切：往上挪正好那么多
else return                                                   // 全可见：一个像素都不动
const max = Math.max(0, document.documentElement.scrollHeight - window.innerHeight)
window.scrollTo({ top: Math.min(Math.max(window.scrollY + delta, 0), max) })
```

三条配套的：
- **`max` 必须夹**：键盘弹出后 `.wb-page` 的 `padding-bottom` 加了 `--kb`，
  文档变高，不夹住会滚到「文档底」以外。
- **弹层里的框不参与**（`el.closest('.van-popup')` 就 return，坑 23）——
  判的要是**聚焦的那个元素**，不是被 `setAvoidTarget` 换掉的避让目标。
- **避让对象可以比聚焦元素大**（`setAvoidTarget`）：例句编辑时要保证**整行**
  含译文和「改好了」按钮都在键盘上方，否则用户得先收键盘才收得了尾。

## 42. 骨架屏本身也是一次跳变 —— 要让**首帧**就有内容

**症状**：把「找不到这个意思」换成骨架屏之后，用户仍然报
「点进去一瞬间会短暂显示一个别的UI，看不清」。骨架屏明明什么都没说。

**判据（这次抓到了硬证据）**：`adb screencap` 抓不到（一次几百毫秒，
而闪烁只有一两帧）。用 CDP 的 `Page.startScreencast` 逐帧录下来，
切页那一帧单独看：

```
001-1134ms-after.jpg   9 KB   ← 闪的那一帧：只剩一张灰条卡片，标题栏都是空的
002-1168ms-after.jpg  29 KB   ← 真正的内容
```

**真因**：跳转的时序是 **mount → 渲染第一帧 → await 读库 → 第二帧**。
不管第一帧渲染什么（错误文案、骨架屏、空页），**它都是一次可见的跳变**。
骨架屏只是把「说假话」换成了「页面空一下再突然长出来」。

**怎么避免**：**首帧就用内存里已有的数据渲染**，一次 IndexedDB 都不用查。
本项目的四张表本来就常驻内存（搜索/统计/训练队列都在用），写入钩子
（`Table.hook('creating'|'updating'|'deleting')`）保证它们永远是新的：

```ts
// db.ts：缓存里同时留着 promise 和解析后的值
export function cachedNow<T>(key: CacheKey): T | undefined { return cache.get(key)?.v as T }
export function senseNow(id: string) { return cachedNow<Sense[]>('senses')?.find(s => s.id === id) }

// 页面：首帧同步读，读不到才退化成骨架屏
const loading = ref(!readyFromMemory(props.id))
```

再加一条：**「哪张表热」不能靠碰巧**。从词库进单词页没例句缓存、
从单词页进意思页有 —— 同一段跳转代码，闪不闪取决于用户之前去过哪儿。
所以启动时 `void warmTables()` 统一预热（真机四张表约 15ms，不 await，
不阻塞首屏）。

**同样的问题不止二级页**：底部 tab 的词库页也是「先出一帧『正在读库… · 0 词』，
再出列表」（screencast 量到 15 KB vs 稳定 37 KB）。四个 tab 全都要首帧同步出内容。

**次要信息宁可晚到也不要假数**：例句条数没算出来之前**不写「0 句」**，
否则「假数 → 真数」又是一次跳变。

**怎么验证**：`scripts/verify_docs.py` 的守卫只能判「代码写没写对」，
判不了「屏幕上有没有闪」。后者靠 `app/web/tests/screencast_frames.mjs`：
CDP `Page.startScreencast` 逐帧录下来切页那几帧，中间帧明显小于稳定帧
（实测闪的那帧 9 KB vs 稳定 29 KB）就是闪了。逐帧签名（坑 29）用来定位
「闪的是什么」，screencast 用来判「还闪不闪」—— 两者互补。

## 43. 「还没读」和「确实没有」必须两个值

**症状**：打开 app，首页第一帧是「**词库还是空的 / 先去词库导入一份词库**」，
6ms 之后卡片才长出来。库里明明有词。真机逐帧录下来是硬的：

```
001  17.8 KB   ← 闪的那一帧：整屏只剩「词库还是空的」
002  28.8 KB   ← 真正的卡片
```

**判据**：录屏中间帧明显偏小；把那帧打开一看，是一句**关于用户数据的话**。

**真因**：坑 42 给了一组「首帧从内存同步读」的函数，但首页漏了 ——
`const card = ref(null)`，`onMounted` 才去读。于是第一帧的 `v-else`
必然命中空状态分支。骨架屏是对的，问题是这里**根本没有骨架屏**：
只有一个值 `null`，同时表示「还没读」和「读完了确实没有」。

**为什么这一帧比坑 42 那帧严重**：42 闪的是一张灰条卡片，是**没说任何话**；
这一帧说的是「你的词库没了」。用户看到的是一句明确的假话，
而假话会引发动作（去导入一份）—— 从「闪了一下」升级成「用户被误导去干一件事」。
**一句话记住：加载态不许对用户的数据下结论。**

**怎么避免**：三态分开，`undefined` 与 `null` 各司其职。

```ts
// undefined = 还没读（表没热），null = 读完了，确实没有
const card = ref<Card | null | undefined>(randomCardNow())
const stats = ref<Stats | undefined>(loadStatsNow())
```

```html
<div v-if="card" class="stage">…真卡片…</div>
<div v-else-if="card === undefined" class="stage skel">…骨架…</div>
<div v-else class="stage">「词库还是空的」</div>
```

配套两条：

1. **同步版和异步版必须共用一份算法**，否则迟早算出两个不一样的数字。
   把 `pickCard` / `computeStats` 抽成纯函数，`await` 只负责拿表。
2. **别只改一处就以为全好了**：守卫要按页数列，别按函数列 ——
   42 的三条断言是按页写的（单词页/意思页/词库页），首页当时就没进名单。

## 44. 写死 2000 的 z-index 会被 Vant 弹层压住

**症状**：点「复制到剪贴板」，复制成功，toast 也弹了 —— **但看不见**，
被底部弹层盖得严严实实。用户看到的现象是「复制好像没成功」。

**判据**：`document.querySelector('.toast')` **存在**且 `textContent` 正确，
但 `elementFromPoint(它的中心)` 返回的是 `.van-popup`。
DOM 里有、用户看不见 = 层级问题，不是没触发。

**真因**：Vant 的层号**不是常量**。`vant/lib/composables/use-global-z-index.js`：

```js
let globalZIndex = 2e3
const useGlobalZIndex = () => ++globalZIndex   // 每挂一个弹层类组件就 ++
```

于是第一个弹层是 2001、第二个 2002…… 本项目的 toast 写的是 `z-index: 2000`，
**比任何一个弹层都低**。没有报错、没有日志、console 干净 ——
只有「东西存在但看不见」。

> 同一个数在别的项目里是对的：这是照抄 Vant 示例里的 `z-index: 2000`，
> 而那个例子里根本没有弹层。**照抄的常数只在那份示例的前提成立时成立。**

**怎么避免**：

1. 轻提示这类「必须永远看得见」的东西，取一个明显高于 Vant 计数器的值
   （`9999`），别去猜它现在涨到几了。
2. **该收的弹层要收**：复制成功顺手 `emit('close')`，
   下一步（切去 AI 粘贴）本来就不该被一块 88dvh 的弹层挡着。
   **失败分支不收** —— 提示语是「请手动选中复制」，那条路要看得见文本才做得到。
3. 配色跟着 token 走。原来 `rgba(28,30,42,.92)` 一块近黑，在暖白底 +
   靛蓝主色的界面里像一块不属于这里的补丁；改成和 `.wb-card` 同源的
   白底 + 细边 + 软阴影 + `--wb-ink`，才像是这个 app 自己长出来的东西。

## 45. 固定栏被拖走不是 DOM 干的，而且注释里写着「已禁」

**症状**：列表滚到边缘继续拖，顶栏和底部 tab 栏被一起拖出屏幕外一小段，
有弹性感。原生 app 里同样操作栏不动。

**判据**（两条都要，缺一不可）：

```bash
node app/web/tests/overscroll_probe.mjs doc down
#   底栏 .fixed 位移 : 0 px
#   状态栏 .sb 位移 : 0 px
#   scrollY 变化   : 0 px
```

DOM 的 `getBoundingClientRect().top` 一动没动、`scrollY` 也没变。
**DOM 是清白的** —— 屏幕上看到的位移发生在 DOM 之外。

**真因**：两套机制被混成了一件。

1. **DOM 侧**（网页能管）：`overscroll-behavior`。越界时浏览器不移动文档，
   所以 fixed 的栏天生不动。
2. **窗口侧**（网页管不了）：`targetSdk ≥ 31` 默认开
   `crossWindowStretchEffectsEnabled`。WebView 一报告越界，
   **系统给整个窗口做拉伸位移**。固定元素长在这个窗口里 → 跟着动。

所以「fixed 就该不动」这个推理是断的：fixed 相对的是**视口**，
不是**窗口**。原生 RecyclerView 的回弹在列表内部做，栏不在绘制范围里，
才天然「列表弹、栏不动」。

**同时挖出一个更难看的**：CSS 里明明写着「橡皮筋必须禁在 html 上」，
注释还解释了为什么。真机一量：

```
html_x: "none"   html_y: "contain"
```

```css
overscroll-behavior: none;          /* 简写 */
overscroll-behavior-y: contain;     /* 长写，把 y 覆盖成了 contain */
```

**注释说的是 none，生效的是 contain。** 而 contain 的语义是
「不把越界传给祖先，**自己照弹**」—— 作者理解反了。
它不报错、不留痕，只有 `getComputedStyle` 量一下才知道。

**怎么避免**：

1. 要「栏不动如山」就用 `none`；`contain` 只挡「传」，不挡「自己弹」。
   **两者不可兼得**（完整取舍见 [D34](../decisions/D34-固定栏与橡皮筋.md)）。
2. **每个滚动容器都要显式写**，别留默认 `auto` 的口子。
   本项目第二处滚动上下文是弹层体 `.sh-b`，原先是 `auto` ——
   自己会弹、还把越界传给祖先。
3. **注释不能当判据**。要么把注释改成机器检查（`verify_docs.py` 里
   「html 禁橡皮筋用 none」断言全仓不得出现 `overscroll-behavior-x/y`），
   要么就别写这种声称状态的注释。坑 42 也是同一根因：
   「已经修好了」这句话本身不产生任何效果。

## 46. 自己会滚的框把页面也堵住了 —— 传递和橡皮筋是两件事

**症状**：更多页三个清单各自限高滚动（`.cap-list`，236px）。
在清单里竖向拖，**页面不滚了**；清单自己只多滚了 52px 就停住。
用户被卡在一个小框里，一屏只能走 50px。

**判据**：量两个 `scrollTop` / `scrollY` 的变化，不要只看页面：

```
第一拖：清单 0 → 52（它的全部余量），页面 0 → 0
第二拖：清单 52 → 52（不动了），页面 0 → 48   ← 本该在这一拖就开始滚页面
```

**真因**：把 D34 的结论用错了地方。`overscroll-behavior: none`
不只关掉橡皮筋，**它把「滚动传递」也一起关了**。
清单滑到头之后本该把滚动交给祖先文档，这时也被挡住 ——
于是「撞墙」。

**关键是要分清三件常被混为一谈的东西**：

| 值 | 自己会橡皮筋 | 会把滚动传给祖先 |
|---|---|---|
| `auto` | 是（但是否真出效果看浏览器） | 是 |
| `contain` | 是 | 否 |
| `none` | 否 | 否 |

**传递 ≠ 橡皮筋**。橡皮筋的最终受害者是**窗口**（系统拉伸，坑 45），
而传递的受害者只是**祖先滚动容器** —— 祖先滚不滚是页面自己的事。

**怎么避免**：看这个框**下面是什么**：

- 框下面是**页面**（更多页的清单框）→ 要 `auto`。
  橡皮筋仍然不会来，因为文档那边是 `none`（D34）—— 传递不产生橡皮筋。
- 框下面是**一层遮罩**（`Sheet.vue` 的 `.sh-b`）→ 必须 `none`。
  传过去会拖动弹层背后的整页，用户看着像页面在自己动。

两条同时挂进 `verify_docs.py`：只断言其中一条的话，
下一个人照样会把另一条抄过去。

**附带**：三个列表框还有一条铁律 —— **条数要写在框外**
（分段标题上）。被裁掉多少是看不见的；只给一个会滑的框，
用户要么反复滑、要么以为就这些。

## 47. 存下来的格式和解析器对不上 —— 就静默少说一句话

**症状**：导入历史压成一行之后，条目少了两个数。
不报错、不留痕，点开备份文件也知道数据没丢，只是「显示得比原来少」。

**判据**：把**存下来的原文**和解析器的正则并排看一眼。
最直接的办法是造两种格式各一条，断言输出字符串**完全相等**。

**真因**：存库的那条 summary 有两种格式，长得还不一样：

```
内容包批量导入：词+18 义+66 改0 句+33 冲突0     ← 前三项带加号，后两项不带
AI 单词导入：  新增义项0 例句10                 ← 根本不是同一个形状
```

解析器按 `key+N` 一刀切，于是：

1. 「改」「冲突」**永远匹配不上**（它们没有加号）→ 两项静默消失；
2. AI 那条一个词都匹配不上 → 只剩一个光秃秃的词名。

**怎么避免**：

1. 正则里的加号**写成可选**（`\\+?(\\d+)`）；
2. **认得出才翻译，认不出就原样用** —— 对已经是人话的句子再翻译一遍，
   结果只会更糟；
3. 关键是**要有测试**：这个 bug 从写出来到被发现隔了很久，中间全绿。
   `flow_smoke` 里那三条 `importLine` 断言当场就红了。

> 更一般的说法：**凡是「读历史数据」的代码，历史格式就是一份契约**。
> 它可能已经老到没人在用了，但读它的代码必须认得全部已知形状。

## 48. 选错文件时用成功话术报告了一次彻底的拒绝

**症状**：拿 content-kit 的 `cards.json` 去点「导入备份」，
弹出来的是「**恢复完成**，1 处跳过：不是 word.backup 文件」。

什么都没恢复，是整份拒收 —— 但这句话告诉用户「恢复过了」。

**判据**：把提示语里的动词读一遍。`恢复完成` 与实际发生的
`一件都没恢复` 是矛盾的，而矛盾的是**话术**，不是数据。

**真因**：`restoreBackup` 把「不是 word.backup 文件」塞进 `skipped`，
调用方看到 `skipped.length > 0` 就套用「完成但有几处跳过」那个模板。
`skipped` 原本的语义是「**同一份文件里**有几条记录不合格」，
被拿来装了「**整份文件不合格**」这一种完全不同的情况。

**怎么避免**：

1. **整份拒收要说整份拒收的话**：`restoreBackup` 认出格式不对就直接抛错，
   由 UI 说「这份不是备份文件」；`skipped` 只留给「部分跳过」。
2. 更进一步 —— **别让用户需要自己判断文件是哪一种**。
   三种导入件的 `format` 字段各不相同，于是入口合并成一个，
   收到文件先分类再分派（`classifyImport`）。
   合并之前用户面对的是两个按钮和一次二选一，而选错还会被骗。

## 49. 把事件的接收方和处理方绑在一起 —— 事件就进了虚空

**症状**：把 `cards.json` 发到微信，在聊天里点开它 ——
应用启动了，**什么都没发生**。连一行日志都没有。

**判据**：`adb logcat` 里能看到 app 有读文件的动作吗？
能看到的话说明壳子没问题，问题在网页侧。此时在别的路由上吗？

**真因**：监听器挂在「更多」页的 `onMounted` 上，而路由是互斥的：

```
用户停在首页 → 从微信点开文件 → 壳子 evaluateJavascript 派发 wb:import-file
                                     → 此时「更多」页没挂载，没有监听者
                                     → 事件进虚空
```

用户「点开文件时恰好在某个页面」纯属巧合，而巧合不会每次成立。

**怎么避免**：**事件的接收方必须常驻**。

- App.vue（永远挂着）接事件，写进 `bridge.incomingFile` 这个模块级 ref；
- 处理方（更多页）只 `watch` 它。
- 顺手把用户 `router.push` 到处理方所在的页面，否则「处理发生了但用户看不到」。

> 验收这件事有个通用判据：**问「这个监听器在哪些时刻是活的」**。
> 「它在我需要的时候在吗」是没法回答的；「它什么时候不在」可以。

## 50. 百分比在 flex 容器里是相对容器，不是相对视口

**症状**：左右滑动的三个面板，功能都对、数据都在，但**每次看到的
都是第一页的中间一段**：

- 切到「导入历史」，高亮对了，列表里却看不到词名（文字被平推出屏幕左边）
- 切到「回收站」（0 条），满屏是快照那一栏的「回滚」行

**判据**（一眼定位）：量 `rect`，别看内容。

```
视口 336     ← .vp
轨道 1008    ← 3 × 336
面板宽 1008 / 1008 / 1008   ← 都应该是 336
面板左 12 / 1020 / 2028      ← 第 2、3 屏在可视区之外
```

**真因**：

```css
.track { width: 300% }        /* 轨道 = 3 × 视口 */
.pane  { flex: 0 0 100% }     /* ← 这个 100% 是轨道的 100%，不是视口的 */
```

`flex-basis: 100%` 里的百分比解析的是 **flex 容器的内部主轴尺寸**。
面板于是各有 1008px，2/3 屏被推到 x=1020 / 2028。
而切换时的平移量是 `100/N %` 轨道宽 = 正好一个视口宽 ——
于是不管切到第几页，可视区里始终是轨道的前 336px，也就是**第一页**。

**为什么难查**：它不像「点了没反应」，而是**看起来像数据错了**。
「回收站 0 条却有回滚行」会去查数据和删除逻辑，「导入历史没名字」会去查
解析器 —— 而这两处都是好的。真因是一个宽度算错。

**怎么避免**：

1. 面板宽度写成 `calc(100% / var(--n))`（相对轨道 = 正好一个视口宽），
   配 `flex: 0 0 auto`；
2. **这类「看起来像数据错」的现象，先量 rect**。
   记住一条排查顺序：**内容不对时，先分清「数据不对」和「位置不对」** ——
   量 `getBoundingClientRect()` 比读数据快，也比读数据可靠；
3. 守卫直接盯这一行 CSS 的形状（`calc(100% / var(--n`），
   免得改回去。

> 更一般的说法：**百分比总是相对它的包含块**。
> 「100% 等于一屏」只在包含块恰好是视口时成立 ——
> 一旦中间多了一层（轨道、卡片、弹层），这个直觉就失效，
> 而失效方式是**安静地算错**。

## 51. `watch` 只盯一个 query，另一个就被漏掉了

**症状**：从「扫读」点某一句进训练页，能进去、也能答题，但**出的不是点的那一句**。

**判据**：看 URL —— `?solo=<义项>&sent=<句子>` 两个参数都在；
再看题目 —— `sent` 没生效。

**真因**：

```ts
watch(() => route.query.solo, start)          // 只盯 solo
```

从扫读进来时**两个 query 同时变**。`solo` 变了 → watcher 触发 → 重开一轮；
`sent` 也在同一刻变成了新值，但没人读它（`makeQuestion` 不接这个参数）。
于是「点哪句猜哪句」安静地退化成「随机出这个意思的一句」。

同一个坑的上一轮（坑 33）是「不同 query 不重开」，这一轮是
「重开了，但只搬过去一半的状态」—— **同一个洞的两半**。

**怎么避免**：

1. watcher 的依赖要**列全**：`[route.query.solo, route.query.sent]`；
2. 更要紧的是**验收方式**：别只看「点进去能不能答题」，
   要看**出的那句是不是点的那句**。前者永远成立，后者才是需求。

> 泛化一句：**「从 A 传到 B 的状态」有多少个字段，就要在 watcher 里数几个。**
> 少一个不会报错，只会让其中一条路径悄悄走成默认值。

## 52. 写好了却没接上 —— 功能就从来没发生过

**症状**：查「已掌握的词会不会回来」这件事，发现
`srs.ts` 里 `decayIfIdle()` 实现完整、参数表里 `DECAY_IDLE` / `DECAY_IDLE_FACTOR`
齐全、`Progress` 有 `rusty` 字段 —— 而**全应用没有一个地方调用它**。

```ts
if (p.mastered && !p.rusty) return    // rusty 永远是 0 → 恒成立
```

所以一个词一旦标成「已掌握」，**永远不会再回到队列**。
「学完就忘」这件事在数据层从来没发生过。

**判据**（按这个顺序，一步比一步便宜）：

1. `grep` 一下那个函数**有没有被调用**，而不是「有没有实现」；
2. 看它写的那个**标志位**有没有别的写入点
   （`rusty` 全仓只有 `decayIfIdle` 会置 1，其余全写 0）；
3. 问一句「它依赖的字段名对不对」—— 见下一条。

**还有个更隐蔽的原因**：即便接上了也不生效，因为**字段名对不上**。
`srs.ts` 是 `app/srs.mjs` 的逐函数移植，内部一律 snake_case（`last_review`），
而库里存的是 camelCase（`lastReview`）。传进去之后
`row.last_review == null` 恒成立 → **直接 return，不报错**。

**怎么避免**：

1. 判据必须是**行为**：「mastered 且闲置够久的词会回到队列」，
   写一条断言这个结果的测试。源码形状判不出来；
2. 「移植的纯函数」与「调用它的现场」之间要有**一层显式字段适配**，
   并且把它写成一行可读的映射 —— 适配层是移植代码最需要被看见的地方；
3. 写库必须在事务里（坑 25）。

> 这条与坑 45 是同一类：**注释和实现都声称某件事发生了，
> 而唯一能揭穿它的是一条断言结果的测试。**

## 53. 给已经缓存着的表再套一层缓存 —— 然后忘了失效

**症状**：意思页点「合并」把两个义项并成一个。之后新卡的 SRS 起始间隔
慢慢不准 —— 查下来是 `n_senses` 一直按**合并前**的义项数算。

**判据**：

```ts
const nSenseCache = new Map<string, number>()
export function clearSenseCache() { nSenseCache.clear() }   // 全仓零调用
```

**真因**：`senseCount()` 自己开了一个 `Map` 缓存，配一个清除函数 ——
而那个清除函数**从来没被调用过**。于是「合并」改了义项数，
内存里的数还是老的。而它喂给 SRS 的 `n_senses`，
进而决定新卡判成 SINGLE 还是 MULTI、起始间隔跟着错。

不报错、不留痕，只是「新卡的间隔慢慢不准了」。

**怎么避免**：

**别给「已经缓存着的表」再套一层缓存。**
`liveSenses` 本来就常驻内存（搜索、统计、词库都在用），
而 `senses` 表的写入钩子会自动让它失效（`db.ts` 的 `TABLE_CACHES`）。
在已缓存的数组里数一遍是毫秒级，换来的是**不可能过期**。

> 「加一个缓存」和「加一处失效逻辑」是一笔买卖。
> 判据很简单：**这份数据的失效钩子是不是已经存在？**
> 已经存在就别再缓存；不存在才值得拿一次失效逻辑去换查询次数。

顺带加一条守卫：**全仓不许出现「导出了但没人调用」的 `clear*Cache`** ——
一个没人调的清除函数比没有缓存更危险，因为它看起来像是被照顾过的。

**验证这一条时踩的另一个坑（值得单记）**：用 CDP 直接 `indexedDB.open()`
往库里塞一行「闲置 40 天」，结果**衰减完全不触发**，而且第一题确实出现了
army —— 一度以为验证通过。

真因：我那次写库是**从外部绕过了 Dexie**，没走它的写入钩子，
所以 `db.ts` 的内存缓存里那份**还是旧行**；队列用的是缓存，
于是走的是旧行的判定（mastered=0 → 正常进队列），
而真正的新行压根没被读。改完刷新一下页面（缓存重建）才验出真值。

> **用调试器直接改 IndexedDB 骗不了应用** —— 因为缓存本来就是为
> 「应用自己写的」准备的。这不是缺陷，但它意味着：
> **任何靠 CDP 改库的验证，都必须重启应用再看。**
> 否则你会用一个「旧数据走得通」的假象给自己发一张合格证。
> 这个现象和坑 53 是同一件事的两面：缓存救了你，也骗了你。

## 54. 用「呈现状态」去推断「作答状态」

**症状**：训练页点「我不会」，答案其实**已经记进 SRS**（进度真的变了），
但界面上一点反应都没有：选项没染对错色、也没有「下一题」按钮，
于是**卡在这一题上出不去**。刷新一下才发现这题早就算答过了。

**真因**：模板里判断「现在该显示什么」用的是 `revealed`（选项已展开），
而「我不会」这条路只把 `submitted`（作答已提交）置了真 ——
提交了，但没有「展开」这个动作。于是 `v-else-if="!revealed"` 一直命中，
「下一题」那个分支永远到不了。两个状态长得像，含义差一整层：

| 状态 | 是谁 | 谁写的 |
|---|---|---|
| `submitted` | **事实**：我答了 | 作答动作 |
| `revealed` | **呈现**：答案摊开了 | 界面 |

**判据**：界面出现「状态不明」时先问一句：这个状态是**事实**还是**呈现**？
用它来判断「该不该有下一步」的，必须是事实。

**怎么避免**：守卫同时钉三个分支 —— `v-if="submitted"` 存在、
`v-else-if="!submitted && !revealed"` 存在、`reviewing && !submitted` 存在。
只要有一个分支被 `revealed` 抢走就 FAIL。

## 55. 多根节点的组件，收不到父组件传下来的 class

**症状**：扫读列表的行号与句子**对不齐**：句子被挤到第二行，行号孤零零留在上面。

`Extraneous non-props attributes` 警告 → 数一下那个组件模板有几个根节点。

**怎么避免**：组件模板包一个根元素（这里是 `<span class="wb-marked">`），
三个分支放进它里面。守卫断言模板里存在这个唯一的根 `span`。

## 56. 同一个 `<style scoped>` 里两条同名规则会合并

**症状**：真机上扫读从第二行开始，句子整体被挤到下一行。量出来的偏差正好
= 行高 22.5 + gap 9 = **31.5px**，一行都不差。

## 57. 写入被截断的汉字，会静默变成一串乱码方块（U+FFFD）

**症状**：没有症状。TypeScript 编译正常、JSON 解析正常、测试全绿、
文档照常渲染 —— 只是某个词里「有个方块」。这次全仓查出 18 处，
其中最短的一处跨了好几个提交，我审过好几遍都没看见。

**真因**：一次写入把某个汉字切在字节边界上，落盘的就不是那个字，而是
U+FFFD（替换字符）。它**不是**非法字节（那会直接报错），它是一个
**合法的 Unicode 字符** —— 所以编译器、解析器、diff 全都放行。

**判据**：扫字节，不是看界面。

```python
if "\ufffd" in open(p, encoding="utf-8").read(): ...
```

眼睛不算判据：方块在等宽字体里和「缺字」长得一样，而它出现在中文长句里时
人会自动补全，读十遍也读不出来。

**怎么避免**：守卫里全仓扫一遍（源码 / 文档 / 词库；跳过 `node_modules`、
`build/`、`__pycache__`）。一起进守卫的还有另一件同类的静默问题：
**坑 0 的索引会过期** —— 新写一条坑忘了进索引，索引就开始骗人。
所以再加一条：代码与文档里引用到的每个「坑 N」，正文里必须有那一节。

## 58. keep-alive 缓存的是组件状态 —— 「再进一次」不等于重开一轮

**症状**：练完一轮，回首页，再点「去训练」：屏幕上还是刚才那张结算屏

## 59. 按需注册的组件漏了 —— 那一格直接是空的

右边应该有那个开关 —— 空的。没有报错、没有红线，页面看着「就是这样设计的」。

Vue 只 `console.warn` 一句 unknown component，然后**把它渲染成空**。
于是「开关」这个唯一能打开 AI 的东西，界面上根本没有。

**判据**：某个控件「应该在这儿但没有」时，先做这一件事：
搜模板里的 `<van-xxx`，再对照 `vant.ts` 的 import 列表。

**怎么避免**：守卫扫全仓 `.vue` 模板里所有 `<van-*` 标签，转成 PascalCase 与
注册表比对，缺一个就 FAIL。手写注册的代价是可能漏，那就得让「漏」变成红色。

## 附：踩坑时的通用排查顺序

1. **先确认在验证的东西是对的版本**（坑 1、2）
   —— 这一点应该排在最前面，因为「验证了旧版本」会让后面所有排查都白费。
2. **量，别猜**。把模糊感受变成数字：
   `scrollWidth` vs `innerWidth`、`transform` 的实际值、
   `elementFromPoint` 落在谁身上、`scrollY` 到底有没有变。
3. **对比「系统看到的」和「JS 看到的」**。两边对不上，
   基本都是壳层把信息吃掉了（坑 4、5、10）。
4. **手动调一次那个函数**，和渲染结果对比（坑 14）。
5. 最后才怀疑自己的代码语法。
6. **怀疑「闪了一下」就逐帧采样**（坑 29、32、42）。肉眼和截图都会骗人：
   逐帧签名告诉你**闪的是什么**，
   CDP `Page.startScreencast` 告诉你**还闪不闪**（中间帧字节数明显偏小就是闪了）。
7. **「点了没反应」先问是不是缺原生回调**（坑 31、34）：
   WebView 有一堆能力默认是空的（文件选择、JS 对话框），
   症状统一是「点了毫无反应且网页侧无报错」。
8. **「滚得太狠 / 闪了一下」先量差值**（坑 32、41）：
   避让类问题永远先量「应该挪多少」和「实际挪了多少」。
9. **「点了有反应但看不见 / 像是没生效」先查层级**（坑 44）：
   DOM 里有、`textContent` 正确，就是被压住了 —— 拿 `elementFromPoint`
   对一遍，别去查事件绑定。
10. **「内容不对」先分清「数据不对」和「位置不对」**（坑 50）：
    回收站显示别处的行、列表看不到名字 —— 这类现象先去量
    `getBoundingClientRect()`，比去读数据快，也比读数据可靠。
11. **「某个功能好像从没发生过」先查它有没有被调用**（坑 52）：
    不是查「实现了没有」，是查「有没有人调」。
    再查那个标志位有没有别的写入点，最后查字段名对不对（坑 52 的移植适配）。
9. **验收改动后把测试数据清干净，并逐项核对原状态**（坑 40）。
