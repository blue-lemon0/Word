# 淘汰与替换逻辑

> 关联：D15（7884 义项）、`01-句子生成与复用.md`
> 核心命题：**内容会耗尽，也会变坏，两者要分开处理。**

---

## 1. 两类问题，两条通道

| | 句子耗尽 | 句子变坏 |
| --- | --- | --- |
| 现象 | `activeCount = 0` | 句子里这个义项不成立 |
| 发现者 | 系统（水位检查） | 用户 / 质检 |
| 处置 | **补充** | **替换** |
| 状态流转 | `retired` 归档 → 生成新句 | `active → bad` → 立刻生成 |
| 紧急度 | 下次会话前 | 立即（当前题就能换） |

**绝不能把"变坏"当成"耗尽"**。若用户报告"这句 run 是『跑』不是『赛跑』"，
而系统当成句子不足去生成 5 句新 run 句子，用户会反复遇到同样的坏句。

---

## 2. 句子退役（retire）

### 2.1 触发

```
同一句在同一义项上连续答对 3 次  ──>  retired
```

"连续"的实现：在 `session_log` 里查该 `(senseId, sentenceId)` 最近
3 条记录，若全 `CORRECT` 且中间无该句的其他出场，则退役。

### 2.2 为什么退役而不是删除

| 理由 | 说明 |
| --- | --- |
| 归档可回滚 | 误判退役（其实是蒙对的）时能恢复 |
| 保留"练过的痕迹" | 规格 N3：减法做得太干净，验证感就消失 |
| 归档体积可忽略 | 5.5MB 库删除 1 条约 106 字节 |

### 2.3 物理删除

`retired` 数 ≥ 3 时，该句从 `active` 池移出，写入
`data/sentences/_retired.jsonl`（仅留 `text` + `senseId` + 退役时间）。
**在线库永远不无限增长**。

## 3. 坏句替换（replace）

### 3.1 检测来源

| 来源 | 信号 | 延迟 |
| --- | --- | --- |
| 用户手动 | 点「这题有毛病」→ 选原因 | 立即 |
| 系统判定 | 同句同义项被判错 ≥ 3 次（`WRONG` 累计） | 延迟 3 场 |
| 质检器 | 生成时 G5 不通过 | 不入库 |

**用户手动优先**。用户说"有毛病"就是有毛病，不需要系统再确认。

### 3.2 原因分类与差异化处置

用户选的原因不同，处置也不同：

| 原因 | 含义 | 处置 |
| --- | --- | --- |
| 译文错了 | 句子本身可用，译文错 | 只重生成译文，**保留句子** |
| 句子跟义项不符 | G5 失败 | 整句退役，生成新句 |
| 干扰项有问题 | 句子可用，选项组错 | 句子保留，重组选项 |
| 语境太难/太简单 | 难度档不符 | 句子保留，**改难度档标记** |
| 其他 | 未知 | 整句退役，生成新句 |

> 分类的意义：如果每次都整句重生成，用户上报"译文错了"
> 也会导致好句子被丢掉，浪费生成配额且损失已积累的 SRS 状态。

### 3.3 替换的事务边界

```
1. 标 bad（立即落库）
2. 当前题换 Layer 3 兜底句            ← 用户不等待
3. 后台生成 1-2 句新句
4. 新句过质检 → active
5. 若原因含"干扰项" → 额外重算该义项的干扰项池
```

**第 2 步是硬要求**：用户点"有毛病"后必须**马上能继续做题**，
不能干等 LLM。

## 4. 义项淘汰

句子会耗尽，义项呢？会。两种情况：

### 4.1 词库升级导致的义项消失

D15 收敛时丢了 6353 个 ECDICT 义项。若将来放宽 K 值把它们加回来，
或 ECDICT 升级导致某个义项的 gloss 变化：

```
1. 加载新 bundle，逐 (word, senseId) 比对
2. 新旧都有 → 继承 SRS 状态与句池
3. 只有旧的 → 该义项标 archived，句子保留在历史里不参与排布
4. 只有新的 → 新义项，初始 S=0 从零开始
5. archived 义项不参与排布，但历史正确率保留
```

**绝不在 App 运行时做词库升级**。升级是开发机上的批处理动作，
产出新 bundle，App 启动时加载新版。

> **与 D16 的区别**：D16 是一次性的**换源**，新旧义项无对应关系，所以不迁移。
> 本节描述的是同一词库内的**增量升级**，那时 `senseId` 是稳定的，继承进度是合理的。
> 不要用 D15 时代的 Jaccard 模糊匹配来续 SRS——`释义`↔`说明` 这类匹配
> 会把掌握度安到错误的对子上。

### 4.2 主动淘汰低价值义项

若某义项满足：

- 12 个月内从不出现在任何会话（因为排布权重一直很低），**且**
- 用户从未在它身上有过任何作答

则它实际是死数据。**但仍不删** —— 它可能是低频却重要的义项，
只是排布没轮到。删除应由显式操作触发，不自动做。

## 5. 排布权重的自我调整

内容质量之外，还要管"哪些义项值得优先练"。

```
weight(sense) = 0.5 × 近 30 天 WRONG 率
              + 0.3 × 是否 TRAP
              + 0.2 × (1 - 掌握度)
```

排布时按 weight 降序取，而非纯按 SRS 到期时间。
这样**错得多、是陷阱、没掌握**的义项自然获得更高频次。

**掌握度**：`interval / 12`，封顶 1。12 场会话未到期视为完全掌握。

## 6. 生命周期全景

```
                    ┌──────────────────────────────────────┐
                    │                                      │
   词库升级 ──> senseId 仍在 ──> 保留（继承 SRS + 句池）     │
        │                                                  │
        └──> 已消失 ──> archived（保留历史，不参与排布）    │
                                                           │
    ┌──────────────┐   生成   ┌────────┐  质检  ┌────────┐ │
    │ NEED 水位<2  │────────> │pending │──────> │ active │ │
    └──────────────┘         └───┬────┘        └───┬────┘ │
          ▲                    REJECT              │     │
          │                      │           连对3次   标记坏
          │                      ↓                ↓     ↓
          │                  重生成(≤2)        retired  bad
          │                                       │     │
          └───────────── 补充新句 ─────────────────┴─────┘
```

## 7. 关键不变量（实现时必须保证）

1. **任何时刻每个义项至少有 1 道可练的题**（Layer 3 保证，违反即 bug）。
2. **`bad` 句绝不出现在 active 池**（数据库层面用视图过滤，不靠应用层自觉）。
3. **退役是幂等的**：`retire(sentence)` 重复调用不改变结果。
4. **替换不丢 SRS 状态**：句子换掉，义项的 interval/ease 不动。
5. **用户标记优先于系统判断**：`bad` 一旦置位，系统不自动改回 active。
6. **归档只增不删**：`retired.jsonl` 是 append-only，误判可回滚。

## 8. 与数据库的对应

在线库用视图而非应用层过滤，确保不变量 2 在 SQL 层成立：

```sql
-- 有题可练的义项（排布只用这个）
CREATE VIEW v_pool AS
SELECT s.*, COUNT(sc.id) AS active_n
FROM sense s
LEFT JOIN sentence sc ON sc.sense_id = s.id AND sc.status = 'active'
WHERE s.status = 'active'
GROUP BY s.id
HAVING active_n > 0;

-- 错题板（派生视图，不单独存）
CREATE VIEW v_wrong AS
SELECT * FROM srs
WHERE wrong_n > 0
  AND (mastered = 0)
  AND NOT EXISTS (
    SELECT 1 FROM srs_log l
    WHERE l.sense_id = srs.sense_id
    ORDER BY l.id DESC LIMIT 2 OFFSET 1
  );
```

`v_wrong` 的"连续 2 次答对则移除"直接用窗口函数表达，
**不维护第二份状态**——这是 D14 定的原则，此处只是落地实现。
