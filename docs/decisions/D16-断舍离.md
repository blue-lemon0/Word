# D16 · 旧数据断舍离，不做迁移

**日期**：2026-09-30
**状态**：已决策并执行
**取代**：D15 遗留的「68% 复用率」开放项

---

## 1. 问题

D15 把义项源从考纲词频表换成 ECDICT 后：

| | 旧库 | 新库 |
| --- | --- | --- |
| 词 | 3000 | 2998 |
| 义项 | 3641 | 7884 |
| 句子 | 18610 | 0 |
| TRAP | 642 | 0 |

`senseId` 是**按义项在词库中的出现顺序**生成的（`s1`、`s2`、`s3`…）。
新库是另一次切分、另一次分档、另一次去重的结果，编号没有任何对应关系。

`scripts/map_senses.py` 做过模糊匹配（Jaccard 字符集 ≥0.5），结论是
**2475/3641 = 68.0% 可映射**（完全一致 1731、模糊 744），未映射 1164 条。

---

## 2. 为什么 68% 不值得追

迁移的前提是「同一个知识单元换了编号」。但这里不成立：

1. **`senseId` 不同 = 进度无法延续。** 用户的 SRS 状态、错题、掌握标记都挂在
   `(word, senseId)` 上。旧 `lay#s2` 练到 S=60 天，新库里对应的义项是新 ID，
   一行都继承不了。
2. **68% 里有一半是"模糊匹配"。** 释义文本相似 ≠ 同一个义项。
   `释义` ↔ `解释` ↔ `说明` 这类匹配会把用户的掌握度错误地安到新卡上。
3. **成本不对称。** 迁移脚本要处理 1164 条未映射的去留（丢弃？归并？标 archived？），
   还要写校验、回滚、跨版本兼容。个人自用工具不值得。
4. **旧句子质量参差。** 18610 句里 18201 是 LLM 生成的，新库要配 39420 句。
   就算全迁移，也只覆盖一半需求，还要额外验证旧句是否符合新质检标准 G1-G7。

结论：**68% 是"释义文本的重合度"，不是"用户已学进度的重合度"。**
用户明确要求「旧的要么存档要么丢掉，重新打造」。

---

## 3. 决策

**不迁移。归档不可再生产物，删除可再生产物。**

判定标准只有一条：**能不能用脚本再跑一遍得到。**

### 归档 → `archive/2026-09-30-pre-ECDICT/`

| 内容 | 数量 | 为什么不可再生 |
| --- | --- | --- |
| `manual-sentences/MANUAL.tsv` | 405 句 | 人工撰写/精修，是"好句子该长什么样"的样本 |
| `old-senses/TRAP_AND_GLOSSEN.tsv` | 3641 义项 / 642 TRAP | TRAP 是人工判断"熟词僻义"，ECDICT 没有这个信息 |
| `specs/` | v2.1 / v2.2 / v2.4 + 决策台账 | 设计沿革，记录被否决的思路 |

> 逐项说明与恢复方式见 [`ARCHIVE.md`](../../archive/2026-09-30-pre-ECDICT/ARCHIVE.md)。

**注意：这些内容只作参考，不进入新训练池。**
405 条人工句对应的旧 `senseId` 已全部失效；642 个 TRAP 指向的义项多数不在 7884 里。

## 4. 由此产生的代码改动

### `scripts/build_bundle.py`

旧版会**丢弃没有 PASS 句的义项**（`drop_no_pass += 1; continue`）。
这在句子齐全时是合理的去重，但在词库先行的阶段会造成
「7884 个义项里有 7884 个从词库消失」——用打包逻辑掩盖内容缺失。

改为：**没有句子的义项也成卡，`rows` 为空数组。**
新增 `mode` 字段（`FULL` / `PARTIAL` / `SENSES_ONLY`）与 `noSentence`、`withSentences` 统计。

### `tools/index.html`

| 位置 | 改动 |
| --- | --- |
| `pickQueue()` | 过滤掉 `rows` 为空的义项——没句子就没法出题 |
| `nextRow()` | 空卡返回 `null`，不再 `0 % 0 = NaN` |
| `loadCard()` | 分流到 `renderNoSentence()` |
| `renderNoSentence()` | 新增：显示词、词性、释义 + "这个义项还没有例句" + 原因说明 + 「下一题」出口 |
| `renderSummary()` | 全部义项无句时显示「暂时没有可练的题目」+ 现状统计，而不是"你答了 0 题" |
| CSS | 新增 `.nosent` 系列 |

### `scripts/fix_pos.py`（新建）

验证新库时发现：ECDICT 的 `translation` 字段约 0.5% 的中文释义**不带词性标记**
（`translation` 是按词性分块排列的，块内后续条目不重复标记，就像英文
`definition` 里 `n. foo` / `bar` / `baz` 只有首条带 `n.`）。
结果是 **400 个义项 pos 为空**，UI 词性标签空白、同词干扰项排序缺参考。

修复规则（不猜词性）：

| 规则 | 做法 | 覆盖 |
| --- | --- | --- |
| R0 | 剥掉泄漏进释义的 `pl.` 复数前缀（`pl. 议程` → `议程`，pos 记 `n`） | 2 |
| R1 | **继承前驱**：同词内取上一个有 pos 的义项 | 398 |
| R2 | 整词无 pos 时，从 `definition` 每行行首标记按序对应 | 0 |
| R3 | 仍无解则留空，**不猜** | 0 |

修复后 **0 个义项缺 pos**，抽查全部合理（`skilled`→a、`airport`→n、`third`→num）。

### `scripts/emit_senses_b.py`

重写：D16 之前它输出到 `senses_b/` 并与旧库交叉验证以支撑迁移决策；
现在直接写 `data/wordlist/senses/`（写前清空，保证与 json 严格一致），
与归档旧库的对比降级为**信息性输出**。

### `scripts/e2e_d16.js`

新增 24 项验收，覆盖零句最坏情况。核心断言：

- `boot()` 正常走完，`state` 初始化
- 每张卡都有词性、无 `pl.` 前缀残留
- `pickQueue()` 返回 `[]` 而不抛异常
- `nextRow()` 对空卡返回 `null`
- `loadCard()` 渲染出「还没有例句」
- `buildOptions()` **仍能构造 4 个选项**——证明"无句"是内容问题，不是数据结构问题
- 小结页显示待生成数量 7884

## 8. 后续：绕开 LLM 通道直接生成句子（D17 预备）

D16 收尾后，尝试**不经 DeepSeek API、由 opencode（模型本身）直接生成句子**，
绕开"LLM 通道禁用"的限制。

### 结论：可行，且优于 API 路径

| 维度 | DeepSeek API | opencode 直接生成 |
| --- | --- | --- |
| G5 义项唯一性 | 只能看单个义项的释义 | **同时看到该词全部义项**，写 `s3 铺设` 时心里有 `s1 放置` 做对比 |
| span 偏移 | 基本瞎填，需后端修正 | 可用 `--fix-spans` 机械重算 |
| 质检闭环 | 需第二次调用 | 写完立刻跑 `sentence_audit.py`，不合格当场重写 |

判别训练要的正是这种**成对对比感**——这是 API 单点调用的结构性劣势。

### 新增 `scripts/sentence_audit.py`

机械质检（G1/G2/G3/G4/G6/G7 + SPAN + SID + NOTE），**不需要第二次 LLM 调用**。
分工：模型负责语义质量（G4 线索是否真能区辨、G5 唯一性、译文传神），
脚本负责机械校验（词形/句长/生僻词/clue 可定位/偏移/指纹去重）。

### 判据修正（三处，均由实测暴露）

#### 1. SPAN 约定：指向 clue，不是目标词

`content/prompts/stage2_sentence.md` 写 `highlightSpan`：目标词位置。
但实测归档的 404 条人工句 **404/404 都是 `span == clue`**，
且 `renderQuestion()` 用 `<mark>` 高亮它——那是**提示**，不是目标词。

改为按 clue 计算，并提供 `sentence_audit.py --fix-spans` 机械重算偏移。

#### 2. G3 原判据不可满足

原写"非目标词 ∩ CORE 3000 = ∅"。CORE 3000 只收**实词**，
连 `the`/`and`/`of` 都不含，任何正常句子都会 fail。

拿 404 条人工句复查：按此判据 **181/404 = 45% 会被误判**，
误判词是 `up`(11) `exam`(8) `children`(7) `soup`(4) `deer`(2) `strove`(5)——
全是**普通词**，不是生僻词。

改为只拦截真正的超纲生词（`TOO_HARD` 名单，刻意保持很短）。
误判率降到 1/404。

#### 3. G1 需要不规则动词表 + 词干兜底

`laid`/`arose`/`strove` 是规则变形算不出来的。
补 `IRREGULAR` 表（约 90 个高频动词）+ `DERIV_PREFIX` 前缀派生 + `stem_match` 词干兜底。

### 审计器可信度验证

用 404 条人工句反向验证（**审计器必须能复现人工质量，否则不可信**）：

```
PASS 385/404 (95.3%)    剔除 SID 检查（旧库已归档，必然 fail）
真实失败 18 条，集中在 4 个词：
  participate(5)  句子用 share，人义对但目标词没出现
  lay(5)          用了 lie 的形式 lies（不同词）
  transaction(5)  句子用 business，同上
  self(2)         用了 themselves
```

这 18 条是**旧人工句的真实缺陷**，不是审计器误报——
正是 G1 要拦的"目标词根本没出现"。反过来证明 G1 有必要。

### `lay` 试点结果（已达标）

`data/sentences/lay.tsv`：4 义项 × 5 句 = **20 条，20/20 PASS，4/4 义项达标**。

自审中改掉的 5 处问题（都是 G5 语义，机械规则查不出来）：

| 原句 | 问题 | 处理 |
| --- | --- | --- |
| They laid grass seed on the bare soil. | 「播种」不是「铺设」 | 改为 `laid a new road` |
| He laid out a neat plan for the project. | 制定计划 = devise，非「布置」 | 改为 `laid out a new park`（空间布局） |
| The soldiers laid out their weapons on the floor. | 实为「摊开」，与 s1 难分 | 删除，换 `laid out the schedule`（arrange） |
| She laid three eggs in the basket that morning. | 主语 `She` 会读成人生蛋 | 改为 `The bird` |
| He laid his coat down before entering the room. | `laid down` 是躺下的习语 | 改为 `laid his coat on the chair` |

**结论：G5 必须逐句人工过一遍。** 机械规则全绿的句子里，语义错位仍有 25%。

### 测试基线从「零句」改为「结构自洽」

补第一句后 `e2e_d16.js` 5 项 FAIL，都是断言钉死在 `sentences = 0` /
`mode = SENSES_ONLY` / `可练义项 = 0`。语料是递增的，钉死 0 会在每次生成后误报，
改为校验不变式：

- `mode` 与句数一致；`withSentences + noSentence == cards`
- `sentences == sum(len(rows))`
- span 全部精确指向 clue
- 有句义项走完整出题链路：`nextRow` → `startSolo` → `<mark>` 高亮 → `revealOptions` → 5 个选项

e2e 从 26 项扩到 **39 项**，新增「有句义项」分支的端到端验证。

顺带修掉两个测试自身的 bug：

- `pickQueue()` 返回的是 **id 字符串数组**不是 card 对象，用 `hasRows(c)` 判全是假失败；
- `document.body.innerHTML` 混着内联 `<script>` 源码，
  而「暂时没有可练的题目」这个字面量就写在源码里 → 假阳性。改判 `viewSummary`。
