# D17 · 存储分层：内容用 bundle，进度用 SQLite

**日期**：2026-10-03
**状态**：已决策并实现
**取代**：`docs/design/05-数据模型-SQLite.md` §2 的 7 表方案（改为其 MVP 子集）
**触发**：需求是「尽快跑通最小循环 + 学习进度持久化」，必须先回答"TSV 还是数据库"

---

## 1. 问题不是二选一

「用 TSV 还是 SQLite」这个问法把两类数据混在一起了。它们的方向相反：

| | **内容层** | **进度层** |
| --- | --- | --- |
| 是什么 | 7884 义项 + 最多 39420 句例句 | SRS 状态 + 作答流水 |
| 谁写 | 只有构建脚本，批量，一次性 | 用户运行时，每次答题一行 |
| 读法 | 几乎全量读进内存 | 按到期/权重做范围查询 + 排序 |
| 变化 | 句子生成完就不再变 | 永久累积，按天增长 |
| 要事务吗 | 不要（不可变快照） | **要**（一次作答要么全生效要么全不生效） |
| 要幂等吗 | 不要 | **要**（网络重试不能把 S 灌成两倍） |
| 随版本 | 跟 App 走，可整体替换 | **跨版本必须保留** |
| 量级 | 静态 7884 行 + 动态 4 万行 | ≈1 万行/年 |

结论：**内容不进数据库，进度必须进数据库。**

---

## 2. 为什么内容不能放进 SQLite

1. **词库是要被人审、要能 diff 的资产。** 放 DB 里就没法 `git diff` 看
   「`lay` 的 s2 释义改了什么」，补 TRAP 标记、补 glossEn 都变成写 SQL。
2. **bundle 要被三方读**：原型、质检脚本、将来 App 的导入器。
   `json.load` 一行就够，DB 还要先建表再导。
3. **升级 = 换文件，不是写迁移脚本。** D16 已经踩过一次：
   换源时 `senseId` 全变，任何 `INSERT OR IGNORE` 合并都会留下脏映射。
4. **7884 行只读数据的 SQLite 收益是零。** 整个 bundle 0.87 MB，
   `JSON.parse` 一次到位；放进 DB 只是多一次导入和一个 0.3 MB 的冗余副本。

## 3. 为什么进度不能继续用 TSV

进度如果也用 TSV，会踩四个坑：

1. **「今天该练哪 20 张」要扫全表 + 排序**，每次开场都做；
   状态一变缓存就失效。
2. **一次作答要同时改 3 处**：`card_state` 一行 + `review_log` 一行。
   TSV 没有事务 —— 断电或崩溃会让 `review_log` 缺一条，
   而流水是**所有统计的唯一真相源**，缺一条正确率曲线就永久偏移。
3. **幂等做不出来**。`UNIQUE(session_id, attempt_id)` 一行约束的事，
   TSV 得自己扫全文件查重。
4. **崩溃恢复**：写到一半的残行。

顺带说明 05 §1 否决 localStorage 的理由同样不适用于进度：
那条否决针对的是**装不下 25 MB 的句子内容**，不是装不下进度
（进度一年 ≈ 1 万行 × 80 B ≈ 0.8 MB）。但 localStorage 仍然不用 ——
没有事务，理由同上。

## 4. 落地的形态

```
assets/senses/*.tsv      义项真相源（已有，人可读可 diff）
assets/sentences/*.tsv   句子真相源（已有）
assets/profile/srs_params.tsv   SRS 参数唯一真相源（D17 新建）
        │  build_bundle.py
        ▼
assets/bundle/cards.json  只读内容快照，0.87 MB，随 App 分发
        │  app/db.mjs 的 rebuildCards()
        ▼
data/user.db              运行时进度，SQLite，永久累积
        ├ card        bundle 的投影，可整表重建，不承载真相
        ├ card_state  用户进度，唯一真相源
        ├ review_log  作答流水，只增不改
        └ meta        schema 版本 + bundle 版本
```

### 4.1 为什么还有一张 `card` 表

内容明明在内存里，为什么还要在 DB 里存 7884 行？

因为到期排布与权重排序要 `JOIN tier / is_trap`（`03` §5.2）。不存就得
把 7884 行拉到内存里排序。而 `card` 是**投影**不是内容：
- 不含释义、不含句子
- bundle 一升级就 `DELETE` + `INSERT` 整表重建
- 重建不动 `card_state`（e2e 有断言）

7884 行 × ~40 B ≈ 0.3 MB，换来「排布/到期/概览全是纯 SQL」。

### 4.2 MVP 只做 4 张表，不是 05 的 7 张

05 §2 的 7 表里有 `sense` / `sentence` / `new_word` / `user_flag` / `setting`，
现在都用不上：

| 05 的表 | D17 的处置 | 何时需要 |
| --- | --- | --- |
| `sense` | **删**，bundle 里有 | 永不 |
| `sentence` | **删**，bundle 里有 | `02` 的句子轮换（seen_count / 退役 / 指纹去重）真正开工时，用 `ALTER TABLE` 加 |
| `srs` → `card_state` | 改名 + 加 `due_at` | 已有 |
| `session_log` → `review_log` | 改名 + 加 `attempt_id` | 已有 |
| `new_word` / `user_flag` / `setting` | 推迟 | 对应功能开工时加 |

先窄后宽：4 张表跑通循环，等真要句子级轮换时再加表，
**已有进度不受影响**（`ALTER TABLE ADD COLUMN` 不动数据）。

## 5. 实现过程中发现并修正的 4 个真 bug

全部由 `scripts/e2e_loop.mjs`（78 项）暴露，不是推测。

### 5.1 `due_at` 必须单列存

05 §3 的 `v_due` 写的是 `last_review + stability*86400 <= now`。
但引擎排期用的是**答对前**的 S（`间隔 = S_before × ef`），
而 `stability` 存的是**答对后**的 S（`= S_before × (1+ef)`）。

两者差一个 `(1+ef)` 倍。主义 s1 首答：引擎说 2.04 天后到期，
视图算出 4.08 天 —— **实际到期时间比 App 告诉用户的时间晚将近一倍**。

改为 `card_state.due_at` 单列，视图直接读它。

### 5.2 难度漂移的符号写反了

`03` §4.2 原文：

```
D ← clamp(D + 0.35×(grade - 4), 1, 10)
```

但该节自己的注解写的是「**WRONG 时 D 上升，FAST 时 D 下降**」。
公式给出的恰好相反：答对把 D 推高、答错把 D 拉低，
于是 `ease_factor` 反向生效 —— 越会越难、越错越简单，
整个 S/D 分离的地基是反的。

实现按注解取号：`D += D_DRIFT × (4 - grade)`。
修正后 `WRONG` 让 D 从 5.0 → 7.8（`ef` 1.02 → 0.68），方向正确。

### 5.3 错题板的移出条件只查了一条

05 §3 原文：

```sql
AND (SELECT result ... LIMIT 1 OFFSET 1) = 'CORRECT'
```

只查了**倒数第 2 条**。历史是 `[对, 错]` 时它返回 `CORRECT`，
于是这张卡被当成"已连对 2 次"而移出错题板 —— 而它明明刚答错。

改为两条都查：`最近一条 = CORRECT AND 倒数第 2 条 = CORRECT`。

### 5.4 幂等键不能是 `(session_id, word, sense_id)`

第一版用 `UNIQUE(session_id, word, sense_id)` 做幂等，e2e 立刻挂：
同一场里 `lay#s1` 第二次作答被静默丢弃。

但同一场里重复出现同一张卡是**合法设计** —— `03` §4.1 的
「WRONG 后至少 2 小时再现」就会落在同一场。

正确的幂等键是 **`attempt_id`**：`/api/next` 每出一道题发一个，
客户端作答时原样带回。同一次出题的重复提交撞同一个 `attempt_id` 被折叠；
同一张卡换个 `attempt_id` 再出现则正常记录。
HTTP 层再加一道 `attemptId` 与当前题不符就 409，挡住"拿上一题的答案乱交"。

## 6. 最小循环已经跑通

```
node app/server.mjs      →  http://127.0.0.1:8777
```

首页 → 三步答题（先回忆 → 显示选项 → 判对错+译文）→ 小结。
进度落 `data/user.db`，关掉浏览器、重启服务都在。

| 验证 | 命令 | 结果 |
| --- | --- | --- |
| SRS 数值 + 持久化 + 幂等 + 事务 | `node scripts/e2e_loop.mjs` | 78 PASS / 0 FAIL |
| 真起服务走完一整场 | `python scripts/smoke_http.py` | 19 PASS |
| 公式推演（与 JS 同一份参数） | `python scripts/verify_srs.py` | 通过 |
| 零句最坏路径回归 | `node scripts/e2e_d16.js` | 39 PASS |
| 词库与文档数字一致 | `python scripts/verify_docs.py` | 37 项 / 0 失败 |

**注意实现栈**：Node 内置 `node:sqlite`（SQLite 3.51），零 npm 依赖。
SQLite 方言与 Android 原生 SQLite 在本项目用到的子集内完全一致，
`app/schema.sql` 可以直接搬进 `SQLiteOpenHelper`。

## 7. 顺带修掉的 tier 断链

`emit_senses_b.py` 把分档写进 `note` 列（`note=tier=T1`），
而 `build_bundle.py` 读的是 `tier` 列 → **bundle 里 7884 张卡 tier 全空**，
`tools/index.html` 的档位标签永远不显示。

这类"写一处读另一处"只有让校验覆盖到下游才拦得住，
所以 `verify_docs.py` 新增 4 项：正式词库 tier 列非空 / bundle tier 无空值 /
bundle 与词库一致 / 每词义项数 ≤ `keep[tier]`。

修完 bundle tier 分布：T1 2401 / T2 3427 / T3 1950 / T4 106。
