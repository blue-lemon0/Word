# D32 · 应用搬到浏览器端：Vue 3 + IndexedDB，义项用内部 UUID 锚点

**日期**：2026-10-17
**状态**：已决策并实现
**触发**：设计稿 `docs/DESIGN-词库系统v2.md` —— 判据不是「词库多大」，
而是**改起来贵不贵**。改一句例句要重打包内容包、发版、重启服务，
这个摩擦让「随时能改」变成空话。
**取代**：`app/server.mjs` 作为 UI 提供者（D17 定的「进度进 SQLite」仍然成立，
只是库从 `app/state/user.db` 搬到浏览器的 IndexedDB）

---

## 1. 三个决定

| | 决定 | 一句话理由 |
|---|---|---|
| 1 | UI 从单文件原型重写成 **Vue 3 + Vite**，数据落 **Dexie/IndexedDB** | 编辑在本地发生，不必过服务端；顺带离线可用 |
| 2 | 学习进度锚点从 `word#senseId`（`'s1'`）换成**义项内部 UUID** | 义项一重排，`'s1'` 就指向另一个意思，进度会**静默**串错 |
| 3 | `app/server.mjs` 退成骨架（托管交接区 + 跑 `tools/`） | UI 不再需要它；SRS 参照实现与工具仍要它 |

界面结构（首页 → 单词页 → 意思页 三级 + 四个底部 tab）与取舍见设计稿，
实现台账见 [`app/web/README.md`](../../app/web/README.md)。

## 2. 「内容不进库」这条还成立吗

D17 §2 说内容不进数据库，理由是「内容是要被人审、要能 diff 的资产」。
现在内容层**进了 IndexedDB**。这不是推翻那条规则，而是它换了主语：

| | 内容真相源 | 浏览器里那份 |
|---|---|---|
| 是什么 | `content-kit/data/**` 的 TSV / YAML | Dexie 的 `words`/`senses`/`sentences` |
| 谁写 | 构建脚本 + 人工审 | 用户（就地编辑、AI 导入） |
| 能不能删 | 不能，是资产 | **能，删了从内容包或备份重新灌** |
| 怎么审 | `git diff` | 导出 `word.backup` 后 diff |

规矩没变：**真相源只有一处**。IndexedDB 里的内容层是「可丢弃的编辑副本」，
单向来自 `build/bundle/cards.json`，用户改完自己导出备份。
用户改的内容**不会自动回写 content-kit** —— 想回写就导出后人工并进 TSV，
走审计。这样「一个事实只存一处」和「改起来要顺手」两个要求同时成立。

## 3. 为什么锚点必须换成 UUID

`senseId = 's1'` 当主键时，下面四种操作都会**静默**毁掉进度
（进度条数值还在，只是指向了另一个意思，用户看不出）：

| 用户操作 | `s1/s2` 当主键 | 内部 UUID |
|---|---|---|
| 在 s1 前插入新义项 | s1→s2，后面全部漂移 | 进度自动跟着义项走 |
| 删掉 s2 | s3→s2，**s3 的进度挂到 s2 头上** | 存活义项完全不受影响 |
| 调整顺序 | 全部错位 | 全部跟着走 |
| 合并 s2+s3 | 只能留一个，另一个的进度丢失 | 两边相加取高 |

所以 `Sense.id`（UUID，永不变）与 `Sense.slot`（显示编号，可重排）必须分离，
例句与进度都挂 `id`。这不是优化，是正确性问题。
代价：外部格式（`word.import`）不再暴露 `senseId`，只给可选的 `slot` 提示；
导出备份里带 `id`，所以备份换机后进度仍然接得上。

## 4. 导入为什么不是「填表」而是「逐条决策」

AI 可能只补了例句、可能顺手改了中文释义、可能多给了一个义项。
所以导入分两步：`planImport()` 只读地算出差异，`applyPlan()` 按用户
**逐条**选的决策写库。默认：释义**保留本地**、例句追加缺的、新义项采纳、
本地独有义项保留。**不提供「全部用导入的」** —— 批量覆盖就是丢数据的开始。
校验不过（word 不合法 / gloss 空 / 同词内英文释义重复 / 例句无原文）整份拒绝。

## 6. 实现中撞到的 3 个真问题

都不是推测，是测试逼出来的。

### 6.1 IndexedDB 的事务 scope 是硬的（第一次首启就炸）

`importBundle()` 里 `db.importLog.add()` 写在
`db.transaction('rw', words, senses, sentences, progress, …)` **之外**。
IndexedDB 里事务外的写操作直接抛 `NotFoundError`（对象库不在事务 scope 内），
于是首启种子导入到一半整体回滚 —— 表现是「界面一直空着」，
而报错藏在控制台里。修法：把 `importLog` 加进 scope。
导入记录与导入内容本就该同生共死，加进去也是对的。

### 6.2 同一个错在第二处

`mergeSenses()` 的事务 scope 是 senses/sentences/progress，但它末尾调
`normalizeSlots()`，后者会更新 `words.updatedAt` → 同样炸。
scope 少一个表，整个合并失败且不留痕迹。

**教训**：Dexie 的事务 scope 不是「建议」，多表操作要一次性列全，
否则错误出现在离原因很远的地方。`flow_smoke.mjs` 的合并用例现在守着这条。

### 6.3 移植时最容易悄悄错的一处

`quiz.ts` 里的 `n_senses` 一开始填 0，于是 `classify()` 把多义词的
第一个义项判成 `SINGLE` 而不是 `MULTI_S1`，起始间隔全错 ——
**不报错，只是变慢**。这类错误只有拿参照实现逐格比才能发现，
所以有了 `srs_parity.mjs`：400 条随机序列 × 12 步，与 `app/srs.mjs`
的 S/D/间隔/评级/类型判定逐格比对（4800 次），外加
`srs_params.json` 必须与 `app/config/srs_params.tsv` 同源。

## 7. 装机之后的排查：怎么找到「卡死」的

D32 前半段的问题（泄题、全表扫描、找不到义项）都好办——**难的是「卡死」**。
那次真正的原因链条，完整记在这里，因为它示范了三种不同的诊断手法：

| 症状 | 我一开始以为 | 实际是 | 怎么发现的 |
|---|---|---|---|
| 点义项进不去 + 屏幕僵住 | 页面逻辑错了 | **WebView 渲染进程崩溃**，屏幕留着崩溃前那一帧 | `adb shell pidof` 返回空 → 再 `adb logcat -b crash -d` 看到 `crashpad` + `libmonochrome` |
| 读不到义项 | 数据库坏了 | 我自己给 Dexie 加表时**就地改了 `version(1)`**，老用户的库既没新表、代码又以为有 | `indexedDB.databases()` 显示版本对；用 CDP 在页面里直接查 store 与记录，全是好的 |
| APK 里「修好的 bug 还在」 | 没修干净 | **打包脚本见 dist 存在就跳过构建**，装的是旧代码 | 查 `dist/assets/*.js` 里有没有修复的特征串，发现是旧的 |

三条经验：

1. **「卡死」先查崩溃。** 进程没了的话，在界面上怎么找都找不到原因。
   `adb logcat -b crash` 必须显式指定 `-b crash`，默认 buffer 里没有。
2. **别相信「界面上看到的东西」，去问页面本身。** CDP 直连 WebView 之后，
   「路由参数对不对」「库里到底有什么」这种问题一行表达式就能回答，
   比截图快十倍，也不用反复猜。
3. **改数据库 schema 必须升版本。** 就地改已发布的 `version(1)` 是静默失败，
   没有一行报错。回归测试是 `tests/schema_upgrade.mjs`（造旧库 → 用新代码打开）。

完整的工具链与坑位清单在
[`app/web/DEBUG-RUNBOOK.md`](../../app/web/DEBUG-RUNBOOK.md)，
已实测崩溃的组件记在
[`app/web/tests/WEBVIEW-CRASHES.md`](../../app/web/tests/WEBVIEW-CRASHES.md)。
通用版本沉淀成了 skill：`.opencode/skill/web-app-to-native/`。
