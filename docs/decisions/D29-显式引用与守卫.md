# D29 · 显式引用的两条通路，与三个 build 期守卫

日期：2026-10
状态：**已生效。** 现有数据一字未动。

## 背景

D27 开了「人工指定 synset」的口子（`_wordnet_exceptions`）。实际写 decisions 时
立刻暴露：**这条口子只有一条通路，另外三种写法全是坏的**。

## 通路一：`fromLines` 里的 `["wn", name]`

D27 只让 `_wordnet_exceptions` 绕过过滤。decisions 里直接写
`fromLines: [["wn","seed.v.01"]]` 引用一个落在过滤范围内的 synset，仍然失败：

```
[跳过] seed  s4 引用了已被清洗掉的英文行 raw=[('wn','seed.v.01')]
```

**报错完全指不到病根** —— 看上去像「清洗规则错了」，实际是「引用没生效」。
于是两条路都改成同一条语义：`exceptions_for()` 现在同时收集
`_wordnet_exceptions` 与 `senses[*].fromLines` 里的 synset 名。

## 通路二：例外名要能按名解析

`first_word_synsets()` 原来只在 `wn.synsets(word)` 的结果里匹配例外名。
但**首词完全不同的 synset 不在这个结果里**：

```
wn.synsets("sharp") 的 verb synset：0 个
sharp.v.03 的首 lemma 是 strike，只是把 sharp 列在次要 lemma 里
→ 想要它，就得按 synset 名直接 wn.synset(name) 解析
```

顺带加了名字写错时的显式警告（原来静默丢弃）。

## 通路三：synset 名不能猜

写 `sharp` 时我按直觉写了 `sharp.a.01` / `a.02` / `a.03`，真实是：

```
sharp.n.01  a musical notation indicating one half step higher
sharp.n.02  a long thin sewing needle with a sharp point
sharp.a.08  keenly and painfully felt
sharp.a.09  having or made by a thin edge or sharp point
sharp.a.10  (of a musical note) raised in pitch
sharp.s.08  very sudden and in great amount
sharp.s.09  quick and forceful
```

**编号不连续，且形容词/副词跨了 `a.`/`s.` 两个 lexname。** 猜名字的后果是
静默失效 + 误导性报错。所以加了查名命令，写 decisions 前必查：

```
python content-kit/pipeline/resegment.py --synset sharp
python content-kit/pipeline/resegment.py --synset sharp having or made by
```

输出带 `[被过滤: usage=baseball]` / `[被过滤: too_short]` 标记，
一眼看出哪些需要显式指定。

## 更严重的一次：编造义项

`sharp` 我写了「（棒球）三振出局」并引用 `sharp.v.03`。查证：

```
全库含 "strike out (a batter)" 的 synset 只有 1 个：fan.v.01
wn.synsets("sharp") 的 verb synset：0 个
```

**`sharp` 在 WordNet 3.0 里根本没有动词义项。** 那个义只挂在 `fan` 下
（a sharp = 三振手）。我是照着 `fan` 的释义想当然套过去的。

这与 D24 是同一个错误的镜像：D24 是拿「造句难度」当合并理由，
这次是拿「语感」当存在证据。**语感必须落到可查的 synset 上才算数。**

## 守卫一：义项间英文释义不得重复

上面那个编造的义项，是被 `resegment_queue` 的 review 抓到的（path_sim 1.00）。
但那只是碰巧 —— 真正该拦它的是 build 期守卫：

```python
k = _gloss_key(row["glossEn"])     # 同词的义项两两比对
if k in _seen_gloss: bad.append("s%s 与 %s 的英文释义完全相同")
```

**为什么必须 build 期拦**：重复义项 = 重复卡片，glossEn 雷同、例句必然雷同，
而例句审计只查「例句与义项的搭配一致性」，查不出两个义项本身重复。

## 守卫二（修正）：多条边界合并时用 ` / ` 分隔

原来用空格拼：

```
a small hard fruit a mature fertilized plant ovule consisting of an embryo...
```

这在界面上是乱句。改成 ` / `：

```
a small hard fruit / a mature fertilized plant ovule consisting of an embryo...
```

## 一次自证：fromZh 写错会怎样

我把 `seed` 的「萌芽（比喻）」「子孙（后代）」误写成 `fromLines=[2]/[3]`，
而那两条边界是「结实」「播种」。后果：

```
s2（比喻·萌芽）glossEn = "go to seed; shed seeds"   ← 错配
s4（结实·结籽）glossEn = "go to seed; shed seeds"   ← 重复
s2 pos = v.                                        ← 错配（应为 n.）
```

**`fromZh` 规则被绕过，ZH-FALLBACK 的 glossEn 留空就失效了。**
新加的「英文释义重复」守卫当场拦住了。教训：
`fromZh` 不是可选装饰，它是「英文侧零覆盖」的唯一声明方式，
写成 `fromLines` 等于伪造英文证据。
