# D21 · 每词义项上限：现有上限是「防御旧切分」的产物，不是内容规格

日期：2026-10
状态：**发现了一个必须你裁决的问题。** 现有数据一字未动。

## 发现了什么

我把「每词最多留 N 个义项」这套上限查清了它的来历，结果是：**它不是内容决策，
是防御旧切分算法的产物。**

证据一：上限被严格遵守，且大量词正好顶到上限

```
超上限的词: 0        <- 硬上限，不是建议
顶到上限的词数:
   T1: 492 词正好 4 义   （T1 共 663 词，74% 顶满）
   T2: 1037 词正好 3 义  （T2 共 1218 词，85% 顶满）
   T3: 939 词正好 2 义   （T3 共 1011 词，93% 顶满）
   T4: 106 词正好 1 义   （100% 顶满）

每档义项数分布:
   T1 (上限4): 1义:18词  2义:44词  3义:109词  4义:492词
   T2 (上限3): 1义:46词  2义:135词  3义:1037词
   T3 (上限2): 1义:72词  2义:939词
   T4 (上限1): 1义:106词
```

**T3 有 93% 的词顶满 2 义，T4 有 100% 顶满 1 义。**
这不是「多数词确实有这么多义项」，而是「被截到 N 个」。两者在数字上无法区分，
但含义完全相反。

证据二：中文侧本来的义项数远超上限

```
中文侧「每词留几段」的分布（按逗号切，不去重）:
   平均 5.90 段/词，最多的一词 13 段
   而上限是 T1=4
```

证据三：来历明确

```
archive/2026-10-retire/scripts/build_senses.py
  MAX_SENSES = 8
  docs/verify_docs.py:  keep = {"T1": 4, "T2": 3, "T3": 2, "T4": 1}
  注释：「超过 8 义项被截断的词: %d」
```

而中文侧的过度切分（平均 5.9 段/词）正是它要对抗的东西。
**上限的真正作用是「防止过度切分产出几百个假义项」，不是「这个单词只值得学 N 个意思」。**

## 为什么按英文切之后它就不适用了

7 词试点里 3 个词撞上了上限，且撞得非常有代表性：

```
queen   产出 5 > 上限 4：多出「立为女王；做女王」
social  产出 5 > 上限 4：多出「联欢会」
stone   产出 5 > 上限 4：多出「纪念碑」
```

**被上限挡住的恰恰是真实义项。**

- `social 联欢会` —— 这是我上一轮专门加「补洞规则」救回来的，
  英文 definition 四条全是形容词，名词义只能从中文补。**上限把它挡掉了。**
- `stone 纪念碑` —— 上一轮你纠正我之后保留下来的（`memorial stone` 真实用法）。
- `queen 立为女王/做女王` —— 补洞救回来的动词义。

换句话说：**如果当初就套用上限，我修的三个 bug 全部白修。**

## 我的处理方式：不静默截断

`resegment.py` 现在遇到超上限直接**硬错误**，要求 decisions 里显式记录：

```
[跳过] social  超出每词上限 产出 5 义项 > 每词上限 4（T1）：联欢会[n.]
```

**理由：合并同义和截断丢义项是两件事。**

- 合并同义 = 「答复/回答/答辩」本来就是三个意思，归一成一个 —— 内容变准确
- 截断 = 「联欢会」这个意思直接消失 —— 内容变残缺

前者是我该做的判断，后者是**你的内容决策**。所以我把选择权留给你，
不替你决定「联欢会不值得学」。

## 请你裁决：上限怎么办

三个选项，各有代价：

**A. 放宽上限**（比如 T1: 4→5, T2: 3→4）
```
优点：不丢真实义项，与「按英文切」的新边界一致
代价：义项总数从 7884 涨到约 9000+，句子需求从 39420 涨到 45000+
      而且要重新评估 UI 每屏放几个义项
```

**B. 保持上限，截断按优先级选**
```
优点：总量可控，与现有规模一致
代价：需要定优先级（word frequency / 可判别性 / 词性覆盖 / 释义长度）
      我已把 truncate_priority 写进 spec.yaml，但**优先级权重本身是内容决策**
      而且被截掉的仍是真义项，只是「挑一个更值得学的留下」
```

**C. 取消上限，全留**
```
优点：零内容损失
代价：义项总数可能到 11000+；UI 和练习队列要重新设计；
      而且 T4（106 词）现在只有 1 义项，全留可能涨到 3 义项
```

我的倾向是 **A**，理由：

1. 上限当初是为对抗中文过度切分而设，现在换成英文切分这个理由消失了
2. 被挡掉的都是我在试点里**专门修回来的**义项（联欢会/纪念碑/立为女王）
3. 7884 个义项我已经能逐条过，9000 个还在能力范围内；
   而真正稀缺的不是词库质量，是**造句产能**（每义项 5 句）
4. 档位本身已经承担了「优先级」职能 —— T4 只留 1 义项是在说
   「这个词最不值得深入」，这比硬砍 T1 更符合内容直觉

但这会改变总规模，**必须你定。**

## 附带产出：一个有价值的度量

为了判断哪些义项值得写句子，我用 WordNet 的语义距离量化了「可判别性」：

```
词内义项对总数 7752
   path_sim > 0.75  (高度重叠, 疑似同义): 206 (2.7%)
   path_sim >= 0.90 (几乎同义):          10 (0.1%)
```

**好消息：只有 2.7% 的义项对语义高度重叠。** 也就是说按英文切完，
97% 的义项对天然可判别，能造出区分句子。

但也验证了**不能靠它自动合并**：

```
0.90  A: undertake a journey or trip        B: make a trip for pleasure
      ↑ 这俩该合并（都是「旅行」）

0.90  A: accept as true; take to be true    B: follow a credo; have a faith
      ↑ 这俩不该合并（后者是「信仰」，不是「相信」）
```

**得分相同但结论相反。** 所以 `separability_flags()` 只做**提示**不做决策，
阈值写在 spec.yaml，逐词人工确认。这印证了「内容判断不能进代码」。

实测在试点里确实抓到了该合并的：

```
capital  0.80  E1 assets available for use in the production of further assets
              E2 wealth in the form of money or property...
              → 已合并为「资本」

queen    0.80  E2 a female sovereign ruler
              E3 the wife or widow of a king
              → 我判断不该合并（线索 wife/widow vs female sovereign），保留为两条
```

后者证明**人工判断不可省**。

## 代码改动

```
spec.yaml 新增:
   keep_per_tier: {T1:4, T2:3, T3:2, T4:1}      上限成为显式配置，不是代码常量
   truncate_priority: [...]                        截断优先级（等 A/B/C 定了再用）
   separability_path_sim: 0.75                     可判别性提示阈值

resegment.py 新增:
   keep_cap_for(word)                读 spec + tier 查上限
   wordnet_roots()                   离线加载 vendored WordNet，缺失时降级不崩
   first_word_synsets(word, wn)      只收以该词为首词的 synset
      ↑ 必须过滤：wn.synsets("reply") 会返回 answer.n.01，那是「答案」的义项
   separability_flags()              语义距离，只提示不决策
   超上限 -> 硬错误，不静默截断
```
